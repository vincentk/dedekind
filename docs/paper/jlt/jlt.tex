\begin{abstract}
Parametric polymorphism, type classes and structural recursion let a functional programmer state what a program does and have a type checker enforce the statement.
\Cpp{23}, which runs much of machine learning and most embedded devices, has the material for them: compile-time evaluation of ordinary functions and of most of the standard library, concepts, and folds over ranges.
It does not hold a generic function to its declared constraints: the body may use any operation its type argument happens to have.

Under the rules of this paper and a check that a tool performs, some templates can then be classified as meaning what their signatures say, a declared law licenses a faster program, and the compiler carries laws through composition.
What was taken on trust comes out as a list.

This paper characterises a fragment of \Cpp{23} as it ships, with no language modification or compiler extension, and no tool required: a fragment whose generic definitions have types of the prenex fragment of System~F and whose programs are ordinary \Cpp{23} programs.
The fragment is type-class-style code under three rules, called the Juliet Posture (Jlt):
i) values are copyable data and functions are pure and evaluable at compile time;
ii) generic code varies with a type only through that type's concepts and traits;
iii) recursion is structural, over a type or over a value, in a number of steps bounded before the first step.
The posture is meant as a route a team can take through \Cpp{23}, checked by a tool and adoptable one file and one rule at a time.
Its kernel, Featherweight Jlt (FJlt), translates by dictionary passing, as Haskell's type classes do, into System~F extended with data types and iterators.
The image is defined on every well-typed program, and from its target it inherits parametricity and type soundness and, under stated assumptions, termination; that a program and its image compute the same values is a hypothesis, stated and not proved.
Jlt beyond the kernel is a set of derived forms, rewrites into the kernel that are not proved either.

A law about a program is an axiom, a conditional law or a derived law.
The programmer declares the axioms and the conditional laws, the compiler takes them at face value, and it applies the conditional laws mechanically to derive the rest.
What the programmer supplies is not proved, so it has to be listed and audited: a tool lists the declared axioms.
A law licenses an overload written for it, and overload resolution composes such overloads.
From an axiom, through the laws derived from it, to faster code is specialisation, and one function is followed along it: the power of a monoid, which its signature permits to take as many steps as its count has bits.
The paper also exhibits a \Cpp{20} program in which a generic function's result depends on a constraint it never declared, which dictionary passing, as in Haskell, rules out, and which Jlt's second rule forbids.

The evidence presented is
a) the results the image inherits, cited from the literature,
b) a linter that refuses by name what breaks the three rules and admits by type what it does not refuse,
c) a library in a public repository whose modules the linter checks, all but twelve that only re-export, and
d) listings checked by the repository's tests, at compile time and, all but one, at run time.
The claim is one of existence: \Cpp{23} already contains an embedding of a fragment of System~F.
The compiler enforces the rules where the standard requires a check, and the programmer keeps them elsewhere.
\end{abstract}
