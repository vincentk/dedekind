\begin{abstract}
Parametric polymorphism, type classes and structural recursion are the tools with which a functional programmer says what a program does and has a type checker hold it to that.
By contrast, \Cpp{23} is a mainstream multi-paradigm language in which functional programming is one style among many.
It runs much of machine learning and most embedded devices, holds zero-overhead abstraction as a design principle, and its current standard has the material: compile-time evaluation of ordinary functions and of most of the standard library, concepts, and folds over ranges.
It does not, however, hold a generic function to its declared constraints: the body may use any operation its type argument happens to have.

This paper characterises a fragment of \Cpp{23} as it ships (no language modifications or compiler extensions), an embedded language whose programs are ordinary \Cpp{23} programs, which a stock compiler translates into conventional executables.
The fragment is type-class-style code subject to three rules, which we call the Juliet Posture (Jlt):
i) values are copyable data and functions are pure and evaluable at compile time;
ii) generic code varies with a type only through that type's concepts and traits;
iii) recursion is structural, on a type or on a natural number that counts down.
Jlt can then be further decomposed into \emph{sugar} and a \emph{kernel}, Featherweight Jlt (FJlt).
FJlt translates into System~F, the polymorphic lambda calculus that Haskell's type classes translate into.
The translation is total on FJlt and preserves types and evaluation, so an FJlt program inherits the System~F image's termination, parametricity and a value; the sugar is named with its desugaring into the kernel, the paper's working hypothesis.
Along the way it shows that \Cpp{20} concepts with overlapping overloads resolve incoherently in GHC's sense, and adopts GHC's rule.
The evidence is proof sketches in the appendix, listings that compile and run at both binding times by a test in the public repository, a library whose core a mechanical linter holds to the rules, and the compiled output.

What is gained is a language embedded in a mainstream compiler that checks formal claims of a modest but real kind, at compile time, where checking is cheap.
Jlt therefore facilitates the exchange between formal methods and mainstream systems programming:
a formal fragment is embedded in the host language, its correctness guarantees are checked during the build, and they complement the host language's performance and ecosystem.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The case for functional programming has been made the same way for decades, and it is a good case.
A function that depends on its arguments alone can be replaced by its value: programs can be read as equations, rewritten by them, and reasoned about by them~\cite{hughes1989why}.
A function that is polymorphic in a type cannot inspect that type, so its type alone says a great deal about what it does~\cite{wadler1989theorems}.
A class of types with operations and laws lets generic code be written once against the operations and reasoned about by the laws~\cite{wadler1989adhoc}.
The two are one mechanism with two sources of equations: a free theorem is proved from the type alone, for every term, and a law is declared of an instance.
Either becomes a rewrite by Leibniz's law, which Rule~1 conserves (Section~\ref{sec:posture}).
For the declared laws Birkhoff's theorem makes the reasoning complete: an equation follows from the laws by equational reasoning exactly when it holds in every model of them~\cite{birkhoff1935structure,burris1981universalalgebra}.
A class with laws is an equational theory and its instances the models, a variety, and a stronger class has fewer instances, so the constraints describe the structure and the structure licenses the optimisation.
The goal is correctness by construction in Dijkstra's sense~\cite{dijkstra1976discipline}.

The case is usually made in a language built around it, and that is where this paper departs: it makes the case in a strongly typed mainstream systems programming language with a stock compiler and no extensions.
While such languages are not theorem provers, their compilers perform checks of the same kind: a compile-time check is a claim the compiler verifies, and the worth of such a checker when the author is not the one trusted had a recent highlight, machine-generated proofs~\cite{hubert2025olympiad} in Lean~\cite{demoura2021lean} accepted because the checker, not the author, said so.
An executable is already a formal object: a machine runs it with no interpretation, so every claim about it is a claim about something formal, whether or not it does what its author meant.
What daily practice lacks is a way to make such claims and have them checked without leaving the language, and that is what a discipline supplies: a tool combined with a way of working, a set of rules.
This paper documents such a discipline: a fragment of a mainstream systems language, characterised so that some of what a functional language guarantees is recovered at the cost of three rules, inside the mainstream ecosystem.
Performance is why one comes to such a language in the first place, and the rules do not touch it: an optimising compiler already reasons about a program, by abstract interpretation~\cite{cousot1977abstract} and by algebraic laws it is told it may assume, as \texttt{-ffast-math} lets it for floating point, and Section~\ref{sec:binding} shows it pre-computing what the rules make computable.
What the rules address is the other cost, the language's size.

Two things make \Cpp{} a good place to attempt such an embedding now.
The first is where \Cpp{} is: much of machine learning and most embedded devices run on it, and a growing number of the people who write it arrive from Python with a functional vocabulary.
The second is that the standard is large and keeps evolving: a fragment is worth drawing because the whole is too large to work in with confidence, and worth drawing now because \Cpp{23} is the first standard with every ingredient.
The fragment is the \emph{Juliet Posture}, or Jlt: a subset of \Cpp{23} whose kernel reads as System~F.
It is an embedded domain-specific language in Hudak's sense~\cite{hudak1996building}, whose domain is System~F and whose host is \Cpp{23}.
Its programs are ordinary \Cpp{23} programs, type-checked and compiled by an unmodified toolchain, Clang~23 here (Section~\ref{sec:limits}), and its kernel's terms are System~F terms, by the translation of Section~\ref{sec:translation}.
Being a strict subset of \Cpp{23}, it is not a language this paper designs but a fragment it characterises, and an embedding it describes, as an archaeologist uncovers a city rather than as an architect builds a house.
The claim is one of existence, shown by construction: \Cpp{23} contains an embedding of a fragment of System~F, and the listings exhibit it.
It is not a claim that Jlt is unique or canonical, although another fragment drawn to the same ends would, we expect, look much like it.
As in the tagless-final style of Carette, Kiselyov and Shan~\cite{carette2009finally}, the embedded terms are generic code over an interface, here a \cppinline{concept}, and their interpretations are its models.
The name is a nod to structural typing~\cite{pierce2002tapl,cardelli1996typesystems}: in \Cpp{23} a \cppinline{concept} is a predicate on a type's structure, not its lineage, and so a rose by any other name would smell as sweet~\cite{shakespeare1597romeo}.
Figure~\ref{fig:arrows} sketches the arrows between these pieces.

The ingredients are compile-time evaluation of ordinary functions and most of the standard library, concepts, and folds over ranges, and one decision in their evolution matters here:
\cppinline{concept}s as proposed for \Cpp{0x} checked a template's definition against its constraints~\cite{gregor2006concepts,dosreis2006specifying}.
However, \cppinline{concept}s as standardised in \Cpp{20} only check its uses when the template is instantiated~\cite{stroustrup2009remove}.
As a result, a template's body may use operations its constraints do not name.
The designers named the problem at the outset, in 2003: ``crucial aspects of the programmer's understanding of a template cannot be expressed directly in the code for compilers and other tools to use''~\cite{stroustrup2003concepts}.
\Cpp{23} therefore contains the material for a typed functional fragment but does not enforce its boundary.
The fragment has two, and this paper draws both.
The outer one is drawn by the three rules: Jlt is \Cpp{23} within them.
We call it a posture because it asks only for a style of programming: every ingredient is in the ISO standard~\cite{cpp23standard}, implemented by toolchains in wide use, and what Jlt adds is the programmer's discipline.
The compiler holds some of the rules and the programmer the rest, and a linter helps but is not required (Table~\ref{tab:posture}).
The inner one is drawn by the translation: the \emph{kernel}, Featherweight Jlt (FJlt), is the part of Jlt on which $\llbracket\cdot\rrbracket$ is defined, and it inherits from System~F termination, parametricity and a value.
Between the two lies \emph{sugar}, in Landin's word~\cite{landin1964mechanical}, which this paper names and characterises without proof (Appendix~\ref{app:fjlt:closure}), the arrangement being the Haskell Report's, a kernel and the translations into it~\cite{marlow2010haskell}.

\paragraph{Contributions.}
The contribution is a map from a known discipline onto existing mainstream functionality, not a piece of software.
\begin{enumerate}
\item The posture: three rules on standard \Cpp{23}, each with what the compiler checks of it and what it leaves to the author (Section~\ref{sec:posture}).
\item Featherweight Jlt, the kernel: a core calculus whose syntax is a subset of \Cpp{23} as written, with typing, evaluation and a translation into System~F. Three theorems about the translation and three corollaries, with proof sketches (Section~\ref{sec:guarantees}, Appendix~\ref{app:fjlt}).
\item An adequacy argument from \Cpp{} to the calculus, which states its gaps rather than writing around them (Sections~\ref{sec:translation:adequacy} and~\ref{sec:limits}), and the sugar, named with its desugaring (Appendix~\ref{app:fjlt:closure}).
\item An observation about \Cpp{20} concepts: with overlapping constrained overloads, a generic function's behaviour can depend on a constraint it never declared, which is GHC's incoherent instance resolution, by default and silently.
Jlt adopts GHC's rule, and the repository's tool reports a call that breaks it (Appendix~\ref{app:fjlt:typing}, Section~\ref{sec:limits}).
\item The exhibits: every listing in this paper compiles and runs under a stock compiler at both binding times, by a test in the accompanying repository~\cite{Krautler_dedekind_2026}, and is held to the three rules by a mechanical check in the same repository, and that pair is what compliance means here.
\end{enumerate}
Not contributed: the translation, which is Wadler and Blott's~\cite{wadler1989adhoc}; the calculus-with-concepts, which is Siek and Lumsdaine's $F^G$~\cite{siek2005essential}; and complete definition checking: Section~\ref{sec:limits} says what the repository's linter reads and what it misses.


\paragraph{How to read this paper.}
The paper is written for authors of generic \Cpp{} libraries first, with System~F as the warranty and a rule they can apply to their overloads; for those who audit or certify \Cpp{} against a policy, who need to know what a tool does and does not check; for readers of programming languages in the line of concepts and type classes, who want to know what the concepts \Cpp{} shipped still support; and for researchers who arrive from Python with a functional vocabulary and want the performance of \Cpp{} with a guard rail.
The sections follow the arrows of Figure~\ref{fig:arrows}, one each.
Section~\ref{sec:posture} is the right hook, the rules that carve Jlt out of \Cpp{23}; Section~\ref{sec:translation:adequacy} is the left hook, the sugar: which Jlt programs are kernel programs; Section~\ref{sec:translation} is $\llbracket\cdot\rrbracket$, the translation of Featherweight Jlt into System~F; Section~\ref{sec:guarantees} is \emph{eval}, the theorems read back from System~F; Section~\ref{sec:binding} is \texttt{clang++} and \emph{run}, one program at both binding times, and how instantiation relates to the translation.
The bottom edge is where the two readings meet.
The listings follow one example through the paper: \cppinline{concat}, the fold that evaluates a list in a monoid, and \cppinline{times}, its constant list, which a declared law turns into one action, and whose count may be any finite prefix of the naturals.
Section~\ref{sec:limits} says where the arrows are partial, Section~\ref{sec:related} where the work sits, and the calculus is the appendix.

\section{From \Cpp{} to Jlt}
\label{sec:posture}

Jlt is not a dialect and not a library.
It is standard \Cpp{23} under three rules, and a program follows the rules or it does not.
The compiler enforces some of them and we say which.
Each rule has a listing of a few lines, verbatim in the test that holds this paper's listings, up to formatting, qualification, repetitions a comment elides and definitions a listing omits.
The LLVM IR panels are Clang~23's output at \texttt{-O2} for functions the test defines, which it compiles but does not compare.


\paragraph{Rule 1, Substitution: values and pure functions.}
\phantomsection\label{def:rule1}
Every type a Jlt program passes around is \cppinline{std::semiregular}: default constructible, copyable, and nothing else is assumed.
Every function is \cppinline{constexpr} and depends on its arguments alone.\footnote{A \cppinline{constexpr} function may still change its own locals: constant evaluation permits modifying only objects whose lifetime began within it, so no mutation can leak, which is the encapsulated state of \cppinline{runST}~\cite{launchbury1994lazy}.
At runtime the linter of Section~\ref{sec:limits} holds the body to the same condition by closing each channel a mutation could leak through: parameters, results, the object, statics, globals, \cppinline{volatile}, boxes, and escaping closures that capture by reference.}
What the rule conserves is Leibniz's law~\cite{leibniz1686discourse}, that equals cannot be told apart by any operation, at either binding time: a call may be replaced by its value, $e[f(x)] = e[v]$ whenever $f(x)$ evaluates to $v$.
In a programming language the law is referential transparency~\cite{strachey2000fundamental}, and a language where $a = b$ but $f(a) \neq f(b)$ for some $f$ has an equality one cannot reason with.

\begin{listing}[htbp]
\begin{minipage}[t]{0.66\linewidth}
\begin{cpp}
static_assert(std::semiregular<size_t>);
static_assert(std::semiregular<std::pair<size_t, bool>>);

template <std::semiregular T>
constexpr T id(const T& x) { return x; }

static_assert(id(size_t{42}) == 42);
\end{cpp}
\end{minipage}\hfill
\begin{minipage}[t]{0.32\linewidth}
\begin{minted}{llvm}
define i64 @id_rt() {
  ret i64 42
}
\end{minted}
\end{minipage}
\caption{\hyperref[def:rule1]{Rule~1}: Substitution.
\cppinline{T} is a value, \cppinline{const T&} denotes it, and it comes back by value.
\cppinline{id(42)} is a fact the compiler checks.
Beside it, the same call at runtime, \cppinline{size_t id_rt() { return id(size_t{42}); }}, is the constant: its LLVM IR under Clang 23 at \texttt{-O2}, attributes stripped.}
\label{lst:rule1}
\end{listing}

In Listing~\ref{lst:rule1}, \cppinline{const T} and \cppinline{const T&} are one parameter, the second an optimisation the translation erases, since nothing changes the value the reference denotes.
Two consequences keep that exact: a function returns a value, never a reference, and every member function, a call operator included, is \cppinline{const}.
The grammar of Appendix~\ref{app:fjlt} has neither a reference type nor a non-\cppinline{const} member, and the linter of Section~\ref{sec:limits} holds \Cpp{} to the same.
The compiler enforces the rule in part: a \cppinline{constexpr} function that reaches for state fails to evaluate at compile time, but nothing stops a caller from only ever calling it at runtime.\footnote{Boxed values on the heap such as \cppinline{std::shared_ptr<const T>} require special treatment, as there are two heaps with non-overlapping life cycles: the one the running program has at runtime, and the one the compiler simulates while it evaluates a \cppinline{constexpr} function during compilation.
They are values in the sense of this section on two conditions, that the pointee is \cppinline{const} and that nothing asks which box it is.
In practice, support for evaluating them at compile time is absent in \Cpp{23} and arrives with \Cpp{26}~\cite{keir2025constexprsharedptr}.}

\paragraph{Rule 2, Abstraction: a type varies behaviour only through its concepts and traits.}
\phantomsection\label{def:rule2}
Generic code may do with a \cppinline{T} what \cppinline{T}'s concepts and traits say it can, and nothing else.
That is the premise of Wadler's free theorems~\cite{wadler1989theorems}, with concepts and traits in the place of type classes~\cite{wadler1989adhoc}, and what it conserves is the body's independence from the carrier: \cppinline{f<T>} is one generic term applied to \cppinline{T}'s dictionary, so it respects every relation the dictionary respects (Corollary~\ref{cor:parametricity}).

\begin{listing}[htbp]
\begin{minipage}[t]{0.47\linewidth}
\begin{cpp}
using namespace std;

template <typename T, typename Op>
constexpr T unit(Op) = delete;
template <typename T, typename Op>
constexpr bool associative(Op) = delete;

template <unsigned_integral T>
constexpr T unit(plus<T>) { return 0; }
template <unsigned_integral T>
constexpr bool associative(plus<T>) {
  return true;
}

template <typename T, typename Op>
concept IsMonoid =
    regular<T> &&
    requires(const T a, const T b) {
      { Op{}(a, b) } -> same_as<T>;
      { unit<T>(Op{}) } -> same_as<T>;
    } && associative<T>(Op{});
\end{cpp}
\end{minipage}\hfill
\begin{minipage}[t]{0.5\linewidth}
\begin{cpp}
template <> constexpr string
unit<string>(plus<string>) { return {}; }
template <> constexpr bool
associative<string>(plus<string>) {
  return true;
}

template <typename T, typename Op = plus<T>,
          ranges::input_range R>
  requires IsMonoid<T, Op> &&
           ranges::sized_range<R> &&
           same_as<ranges::range_value_t<R>, T>
constexpr T concat(R ws) {
  return ranges::fold_left(
      std::move(ws), unit<T>(Op{}), Op{});
}

static_assert(concat<size_t>(
    array{1uz, 2uz, 3uz}) == 6);
static_assert(concat<size_t,
    multiplies<size_t>>(array{2uz, 3uz, 7uz})
    == 42);
static_assert(concat<string>(
    array{"ab"s, "c"s, "d"s}) == "abcd");
\end{cpp}
\end{minipage}
\caption{\hyperref[def:rule2]{Rule~2}: Abstraction.
Left: the monoid shape: a set which is closed under an associative binary operation \cppinline{Op{}(a, b)} and equipped with a unit element.
The monoid shape is certified for the family of \cppinline{std::unsigned_integral} with signature \cppinline{operator+} and \cppinline{0}.
Right: \cppinline{concat}, the fold that evaluates a list in a monoid, lists being the free monoid, and \cppinline{sized_range} keeps the list finite, as Rule~3 asks.
Some certifications omitted for brevity.
}
\label{lst:rule2}
\end{listing}

Listing~\ref{lst:rule2} illustrates this for a common algebraic structure: the monoid and its fold, \cppinline{concat}, Haskell's \texttt{mconcat}.
\cppinline{concat} uses only what its constraint names, so it is a function of the monoid's record.
A requirement names an operation with its result type, exactly, \cppinline{same_as<T>}, as \cppinline{IsMonoid} does, or up to conversion, \cppinline{convertible_to<T>}.
The second is the language's own, and the library needs it about as often as the first: an operation on small integers returns an \cppinline{int}, so \cppinline{true * true} is an \cppinline{int} and not a \cppinline{bool}.
It keeps Rule~2, because the body may use the result only at the declared type, so the conversion is part of the operation the constraint names (Appendix~\ref{app:fjlt:typing}).
A \Cpp{} compiler checks a template's body at instantiation, against the type supplied, and not at definition, against the constraint; Haskell's type checker does, which is the only reason this is a rule here.
A body that uses what its clause does not name, as the test's \cppinline{twice_loose} uses \cppinline{x + x} under no clause, compiles at \cppinline{double}, whose \cppinline{+} is not associative, and nothing says so.

\paragraph{Rule 3, Descent: recursion is structural.}
\phantomsection\label{def:rule3}
A Jlt program recurses on a structure, and the structure lives in one of two places.
What the rule conserves is the inductive argument, which loses one constructor at every step, so the recursion ends: that is structural induction~\cite{burstall1969proving}, and a language all of whose programs end by it is Turner's total functional programming~\cite{turner2004total}, and the fold's universal property is its equation~\cite{meijer1991functional}, $h = \mathit{fold}\,a$ exactly when $h \circ \mathit{in} = a \circ F\,h$.\footnote{$F$ is one layer of the data type with a hole for the rest, for a list of words $F\,X = 1 + \mathit{Word} \times X$; $\mathit{in}$ builds one more layer, the constructors $\mathit{nil}$ and $\mathit{cons}$; $a$, the algebra, says what to do with one layer once the rest is folded; and $F\,h$ applies $h$ to the rest only.
For \cppinline{concat} the equation is its definition, $h(\mathit{nil}) = \mathit{unit}$ and $h(\mathit{cons}(w, r)) = w \oplus h(r)$, and \emph{exactly when} says that \cppinline{concat} is the only function that satisfies both.}
Either the structure lives in a \emph{type}, a typed term, an array of known length, a parameter pack, and the compiler unfolds the recursion, each call a different specialisation.
Or it lives in a \emph{value}, a natural number that counts down, at either binding time: the length of an interval, or a \emph{budget}, a number the caller supplies before the fold starts, for a computation that has no inductive argument of its own.
In the terms of Meijer et al.~\cite{meijer1991functional}, Listing~\ref{lst:rule2}'s \cppinline{concat} is the first kind, a catamorphism, and Listing~\ref{lst:rule3}'s \cppinline{times} the second, a catamorphism of the bounded unfold \cppinline{repeat(x, ordinal(n))}, which together make a hylomorphism.

\begin{listing}[htbp]
\begin{minipage}[t]{0.55\linewidth}
\begin{cpp}
template <typename N>
constexpr size_t ordinal(N) = delete;

template <typename N>
concept IsFinitePrefix = totally_ordered<N> &&
    requires(const N n) {
      { ordinal(n) } -> same_as<size_t>;
    };

template <typename T, typename Op = plus<T>,
          IsFinitePrefix N>
  requires IsMonoid<T, Op>
constexpr T times(T x, N n) {
  return ordinal(n) == 0 || x == unit<T>(Op{})
    ? unit<T>(Op{})
    : concat<T, Op>(views::repeat(x, ordinal(n)));
}
static_assert(times<size_t>(7, 6uz) == 42);
\end{cpp}
\end{minipage}\hfill
\begin{minipage}[t]{0.43\linewidth}
\begin{minted}{llvm}
define i64 @times_n(i64 %x, i64 %n) {
  %r = mul i64 %n, %x
  ret i64 %r
}
\end{minted}
\end{minipage}
\caption{\hyperref[def:rule3]{Rule~3}: Descent.
Left: a fold over a budget.
\cppinline{times} is \cppinline{concat} of the constant list, \cppinline{n} copies of \cppinline{x}, for a count \cppinline{n} of any finite prefix of the naturals: a chain with its \cppinline{ordinal}, the order embedding onto an initial segment of \cppinline{size_t}.
\cppinline{size_t} is its own ordinal, and the test registers \cppinline{bool} and \cppinline{char} too.
No copies, and copies of the unit, are the unit, without a fold, by the unit law.
Right: the LLVM IR Clang 23 emits at \texttt{-O2} for the function specialised to \cppinline{size_t}, with \cppinline{n} known only at run time, attributes stripped.
}
\label{lst:rule3}
\end{listing}

What the processor runs of Listing~\ref{lst:rule3}'s fold is the panel's one multiplication, though the budget is known only at run time (Section~\ref{sec:binding}).
What the rule buys is termination and, with Rule~2, the System~F reading, data as their own folds after B\"ohm and Berarducci~\cite{bohm1985automatic} (Appendix~\ref{app:fjlt:translation}).
Like System~F, which is strongly normalising and so cannot express every computable function~\cite{girard1989proofs}, Rule~3 trades expressiveness for termination: the programs that halt are not a decidable set~\cite{turing1936computable}, so a language whose every program terminates cannot compute every function, and a bounded search terminates without always deciding the question it was asked.
Jlt pays with a third answer in the kernel, Kleene's \emph{unknown}~\cite{kleene1952metamathematics}, which says that a budget was exhausted.
At compile time each kind of structure meets a counter of the compiler's, a type the template instantiation depth and a value the constant-evaluation step limit, both configurable, and exceeding one is a compilation failure (Section~\ref{sec:limits}).

\section{From Jlt to Featherweight Jlt}
\label{sec:translation:adequacy}

Section~\ref{sec:posture} defined Jlt by its rules, and Section~\ref{sec:translation} defines its kernel, Featherweight Jlt, by a grammar.
This section is the arrow between them, the $-$sugar of Figure~\ref{fig:arrows}.
It summarises which construction of Jlt becomes which term of the kernel, and leaves the lemma for each to Appendix~\ref{app:fjlt:closure}.
Desugaring here means rewriting a program into one that uses only the kernel's constructions and computes the same value.
What it removes are the conveniences the kernel lacks, such as a lambda, an \cppinline{if} statement or a branch on a concept.
The \Cpp{} standard does the same when it defines a lambda as a class with a call operator.
No tool runs the rewriting.
Table~\ref{tab:closure} states it construction by construction: a condition, and the kernel term it yields.
The repository's linter measures that the table names every construction the library writes.

Listing~\ref{lst:desugar} shows the desugaring that matters most: a branch on a concept becomes a family of generic functions.
The stronger concept buys a faster algorithm, as \mbox{\cppinline{std::advance}} jumps for a random-access iterator and walks for the others.
Written as a branch inside Listing~\ref{lst:rule3}'s \cppinline{times}, the specialisation is an \cppinline{if constexpr} on \cppinline{IsSemimodule}.
Desugared, it is the listing's overload, whose constraint contains Listing~\ref{lst:rule3}'s.
System~F has no overloading, so in the translated family each function is a plain function of its constraints' records, and each call is the function its resolution picks.
The bodies keep Rule~2, and the translation makes it visible: equality and the action become \texttt{m.eq} and \texttt{s.act}, fields of records, because a constraint named them, the action up to conversion (Section~\ref{sec:posture}).
For another carrier, such as a matrix, the programmer supplies \cppinline{operator*} and its certificate.
The free theorem and the laws do different work: the first says that Listing~\ref{lst:rule3}'s \cppinline{times} can only build copies of \cppinline{x} with \cppinline{Op}, the second which of those constructions are equal.
The semimodule's laws, $0 \cdot x = 0$, $1 \cdot x = x$ and $(n + m) \cdot x = n \cdot x + m \cdot x$, make $n \cdot x$ the \cppinline{n} copies of \cppinline{x}, by induction on \cppinline{ordinal(n)}.
In Birkhoff's terms the listings descend through varieties: lists are the free monoid, a semimodule over the counts adds operations and laws, so fewer carriers qualify, and the counts are a homomorphic image of the naturals, the initial semiring, with \cppinline{ordinal} a section of the quotient, which is the premise a certificate vouches for, and which the language's arithmetic makes true of \cppinline{size_t} and \cppinline{bool}.\footnote{Only the algebraic shapes are varieties: \cppinline{totally_ordered} is not equational, since a product of chains is not a chain.}
Scalars of type \cppinline{size_t} are the integers modulo $2^{64}$.
So the certificate holds for the unsigned carriers that wrap at a power of two dividing $2^{64}$, which \cppinline{bool}, whose \cppinline{+} saturates, does not, and for no carrier that does not wrap, such as \cppinline{std::string}.
Counts of type \cppinline{bool} are the Boolean semiring, since \cppinline{true + true} converts back to \cppinline{true}, and \cppinline{bool} under \cppinline{||} is a semimodule over it: \cppinline{n} copies of \cppinline{x} are \cppinline{n * x}, which is \cppinline{n && x}.
Counted in \cppinline{size_t}, the same monoid is no semimodule, since $2^{63} + 2^{63}$ copies wrap to none while the copies are \cppinline{true}, and \cppinline{times} folds.
The count type decides the algebra, and the type checker holds it to the certificates.
In the kernel the choice is resolution by specificity (Appendix~\ref{app:fjlt:typing}).
Theorem~\ref{thm:coherence} keeps it coherent, because the declared constraints decide it at each instantiation.
The other kinds of sugar, a lambda or an \cppinline{if} statement, are routine, and Table~\ref{tab:closure} gives each its kernel term.

The theorems of Section~\ref{sec:guarantees} are about FJlt.
For them to say anything about a \Cpp{} program, two things have to hold, and they hold in different ways.

\emph{Every FJlt program is a Jlt program, with the same meaning.}
This direction holds by construction, as Appendix~\ref{app:fjlt:syntax} states.
The grammar of Figure~\ref{fig:fjlt-syntax} is \Cpp{} syntax, and FJlt's evaluation is constant evaluation restricted to it.
For each construct, the standard's rule is the FJlt rule.
Constant evaluation refuses undefined behaviour, so at compile time an FJlt program cannot go wrong silently.
At run time it can (Section~\ref{sec:limits}).
The standard library pieces the grammar admits are taken with their standard meaning, as every \Cpp{} program takes them.

\emph{A Jlt program written in the grammar of Figure~\ref{fig:fjlt-syntax} is an FJlt program.}
This direction is not a theorem, because the compiler does not check two of the rules.
It is also conditional on the grammar, because \Cpp{} has constructions FJlt lacks, and a Jlt program may use them.
Table~\ref{tab:adequacy} lists what a Jlt program may write that the kernel's grammar does not have, and what the kernel has instead.

\section{From Featherweight Jlt to System~F}

Featherweight Jlt is the subset of \Cpp{23} that Appendix~\ref{app:fjlt:syntax} writes down as a grammar.
A concept becomes a record type, an instance a record, a constraint a parameter and a fold an iterator.
Appendix~\ref{app:fjlt:translation} defines the map in full.
The map is total on FJlt: every FJlt program has an image, and Section~\ref{sec:guarantees} says what the image guarantees.
It is partial on \Cpp{}: a \Cpp{} program is an FJlt program only when it keeps the three rules.
Section~\ref{sec:translation:adequacy} is the argument for when it does.
Six of its rules carry the listings' structure, and Table~\ref{tab:rules} states them.

\subsection{Instances with contexts}
\label{sec:translation:contexts}

An instance may itself require instances: the unit of a pair is the pair of units, provided both components have one.
Listing~\ref{lst:rule2}'s instance for the unsigned integrals is the simplest case, one context on one carrier.
In \Cpp{} that is a generic function with a \cppinline{requires} clause, and the clause is the context.
Under translation it is a function from the components' records to the composite's:
\begin{minted}{text}
pair_unit  =  Λ A. Λ B. λ da : MonoidDict A OpA. λ db : MonoidDict B OpB.
                (da.unit, db.unit)
\end{minted}
The compiler applies such functions outside in, as often as the composite nests.
The recursion ends, because a context can only mention proper parts of the type it is for.\footnote{The termination conditions on instance contexts are studied by Sulzmann et al.~\cite{sulzmann2007understanding}.
GHC calls them the Paterson conditions.
The FJlt syntax enforces them by construction, since a context can only mention the type arguments of the operation being specialised.}

\section{From System~F Back to Featherweight Jlt}
\label{sec:guarantees}
% The three theorems about the translation of Section~\ref{sec:translation}
% and Appendix~\ref{app:fjlt}, stated after the exhibits so that each can
% point at one.  Proof sketches in Appendix~\ref{app:fjlt:theorems}; the
% adequacy argument (C++ -> FJlt) is Section~\ref{sec:translation:adequacy}
% and is not a theorem.

The theorems rest on FJlt alone.
Their proofs (Appendix~\ref{app:fjlt:theorems}) are inductions over the grammar, the typing and the translation of FJlt, and never mention the three rules.
The rules are not the hypotheses of the theorems.
They are what makes a \Cpp{} program a term of the calculus the theorems are about, and that step is the argument of Section~\ref{sec:translation:adequacy}.

\begin{theorem}[Type preservation]
\label{thm:preservation}
If $\Gamma \vdash e : \tau$ in FJlt, then $\llbracket \Gamma \rrbracket \vdash \llbracket e \rrbracket : \llbracket \tau \rrbracket$ in System~F.
\end{theorem}

Each \cppinline{requires} clause has become a record parameter.
At each call, the instance the compiler resolved supplies a record of the type that parameter demands.

\begin{theorem}[Simulation]
\label{thm:simulation}
If $e \longrightarrow e'$ in FJlt, then $\llbracket e \rrbracket \longrightarrow^{+} \llbracket e' \rrbracket$ in System~F, and values translate to values.
For closed terms of base type, $e$ evaluates to $v$ if and only if $\llbracket e \rrbracket$ reduces to $\llbracket v \rrbracket$.
\end{theorem}

What a \cppinline{static_assert} sees is what the translation computes, and, by Rule~1, what the runtime computes.
Section~\ref{sec:binding} is this theorem run twice.
The theorem also fixes the notion of equality here.
A notion has to be chosen, since equational reasoning presupposes one, and which one is a question of its own~\cite{mazur2008equal}.
Two closed terms of a carrier are equal when they evaluate to the same value: equality by behaviour, not by identity.
Leibniz's law of Rule~1 then holds by substitution.
That choice is what lets Rule~1 ask \cppinline{std::semiregular} and not \cppinline{std::regular}.
No \cppinline{==} is asked of a value.
A carrier's \cppinline{==} is one more operation of its signature, where a shape asks for it, as \cppinline{IsMonoid} does.
A function object is a value under Rule~1 and has no \cppinline{==}: equality by behaviour accommodates it, and equality by \cppinline{==} would not.

\begin{theorem}[Coherence]
\label{thm:coherence}
The translation is a function of the program: two resolutions of the same constraint at the same concrete types yield the same record.
\end{theorem}

In \Cpp{} this is overload resolution together with the one-definition rule: at concrete types a specialisation is unique, or the program is ill-formed.
It is what makes ``the unit of \cppinline{+} at \cppinline{size_t}'' a phrase with one meaning in a program, and therefore something a law can be stated about.

\begin{corollary}[Termination]
\label{cor:termination}
Every FJlt program terminates.
\end{corollary}

It follows from Theorem~\ref{thm:simulation} and strong normalisation of the target~\cite{girard1989proofs}.
Every step of the program is at least one step of its image, and the image cannot step forever.
The budget in Rule~3 is therefore not a guard against non-termination.
It is how a bound is said.

\begin{corollary}[Parametricity]
\label{cor:parametricity}
A generic FJlt function satisfies the free theorem of its System~F type.
\end{corollary}

By Theorem~\ref{thm:preservation} and Reynolds' abstraction theorem~\cite{reynolds1983types}.
\cppinline{concat} at a monoid can only combine the words by \texttt{op}, starting from \texttt{unit}, which is the free theorem of a fold.
It is also why an instance with a context (Section~\ref{sec:translation:contexts}) can read a composite's law off its components' records.
The composite cannot do anything the components' records do not provide.

\begin{corollary}[Type soundness]
\label{cor:soundness}
A well-typed closed FJlt term of base type evaluates to a value.
\end{corollary}

This is the theorem a reader of Featherweight Java~\cite{igarashi2001featherweight} expects first.
It comes last because it is cheap once the rest is in place.
A closed well-typed term is a value or takes a step (progress, Lemma~\ref{lem:progress}), and it cannot step forever (Corollary~\ref{cor:termination}), so it reaches a value.
Featherweight Java proves progress and preservation over its own rules too.
What the translation adds is the second half of Theorem~\ref{thm:simulation}: the value reached is the value the System~F image computes.


So the theorems transfer to a \Cpp{} program on two conditions.
It is written in the subset, which the compiler checks.
Its generic bodies and loops keep to the two rules the compiler does not check, which the author checks.
Section~\ref{sec:limits} is the list of places where the first condition is harder to meet than it looks.

\section{Partial Evaluation at Build Time}
\label{sec:binding}

Every function in this paper has run twice already.
\cppinline{id(size_t{42})}, \cppinline{concat} on three numbers and on three words, and \cppinline{times<size_t>(7, 6uz)} were each checked in a \cppinline{static_assert}.
The test behind the listings calls the same functions at runtime, on values it did not have at compile time.
Rule~1 is what makes that unremarkable: a \cppinline{constexpr} function of its arguments alone has no binding time of its own.
A \cppinline{consteval} function, an immediate function, is the opposite case: it is evaluated only at compile time, so it has exactly one binding time, which is why Rule~1 asks \cppinline{constexpr} and not \cppinline{consteval}.
Theorem~\ref{thm:simulation} says the two evaluations agree.
That is the presumption of this section: moving a call from compile time to run time changes where it is evaluated, not what it evaluates to.
Both are partial evaluation~\cite{jones1993partial} at build time: the compiler evaluates what it can and leaves the processor the rest.
For a \cppinline{static_assert}, whose arguments are constants, the rest is nothing.
For \cppinline{times<size_t>(x, n)} with \cppinline{x} and \cppinline{n} read at run time, the rest is the fold.
The presumption holds where both evaluations finish and neither meets undefined behaviour.

\paragraph{The two evaluators are different programs.}
In constant evaluation no optimiser runs: the front end interprets a fold one step at a time, and the optimiser that finds Listing~\ref{lst:rule3}'s multiplication sees only the code emitted for run time.
So at compile time only a declared law shortens a fold, chosen by resolution, as for Listing~\ref{lst:desugar}'s overload: it buys at build time what the optimiser finds at run time by itself.

\paragraph{No difference is another value.}
The limits count the evaluator's work and are the compiler's to set: raised, the refused assertion of Listing~\ref{lst:binding} compiles and holds.
Undefined behaviour runs the other way: constant evaluation refuses it, and at run time it passes unseen (Section~\ref{sec:limits}).

\paragraph{The same laws license parallelism.}
Parallelism can be modelled from the hardware, by what threads can do, or from the algebra, by which problems can be split at all, and this paper takes the second.
\cppinline{std::reduce} may regroup and reorder the operands it folds, and the standard specifies its result only for an operation that is associative and commutative, laws that \cppinline{IsMonoid} and \cppinline{IsCommutativeMonoid} declare.
Its parallel policies further ask that the operation introduce no data race, which Rule~1 gives by construction.
So a parallel \cppinline{concat} is one more overload, under \cppinline{IsCommutativeMonoid}, calling \cppinline{std::reduce} with \cppinline{std::execution::par}, and its threads stay inside it.
The laws say when the split is correct, not when it pays: a thread costs more than a step of a fold, only enough work repays it, and that is the run time's to measure.
The shortcut is a run-time one: the overloads that take a policy are not \cppinline{constexpr}, so keeping the compile-time fold beside it needs \cppinline{if consteval}, the last row of Table~\ref{tab:binding}.
And \cppinline{double} under \cppinline{+}, which no shape certifies (Section~\ref{sec:limits}), is the operation whose parallel sum changes from run to run.

\paragraph{A branch on the binding time desugars to its compile-time branch.}
\cppinline{if consteval}, and an \cppinline{if} on \cppinline{std::is_constant_evaluated()}, are how a program can observe its binding time, and FJlt need not have them.
\cppinline|if consteval { A } else { B }| desugars to \cppinline{A}, provided \cppinline{B} computes the same value as \cppinline{A} on every input, so that the program cannot observe the difference after all (Table~\ref{tab:closure}).\footnote{The choice of \cppinline{A} is not arbitrary: it is the branch constant evaluation takes, which is FJlt's evaluation, while \cppinline{B} is typically not constant-evaluable, which is why the program branches at all.}
For the parallel \cppinline{concat} the condition is the free monoid's universal property: a fold over a concatenation is the operation applied to the folds of the parts, by associativity, and commutativity lets the parts come in any order.
So the law that licenses the shortcut also proves that the branches agree.
For an arbitrary branch the condition is semantic, and a reader holds it, as for the part of Rule~2 the linter does not reach.

\Cpp{} does not pass dictionaries, so the translation is a model of what a constrained call means, not of what the compiler emits.
What the compiler does is instantiate.
\cppinline{concat<size_t>} at an array of three is compiled as a separate function, with \cppinline{size_t} substituted and every trait call resolved.
In the model that is the term $\llbracket \mathit{concat} \rrbracket\,[\mathtt{size\_t}]\,d$, with its type and record arguments applied and $\beta$-reduced before the program runs.
Instantiation is partial evaluation of the dictionary-passing term at a static type, so the two agree on every closed term.
That is Theorem~\ref{thm:simulation}, read at the binding time where the records are constants, and nothing of a record survives to runtime.
The listings show the instruction the compiler is left with.
Appendix~\ref{app:fjlt:ssa} follows the term one step further, into the compiler's own intermediate representation, static single assignment form.
That is a functional language too, as Appel put it~\cite{appel1998ssa}, with the fold's state as the parameters of a loop.
What the model is for is the term \emph{before} that evaluation.
Parametricity is a property of $\Lambda\alpha.\,\lambda d.\,\ldots$, and it holds of every instantiation, because each one is an application of that term.
For Go, Ellis et al.~\cite{ellis2022generic} prove the dictionary-passing translation correct and compare it with monomorphisation, which Griesemer et al.~\cite{griesemer2020featherweight} proved correct.
\Cpp{} only ever does the second, and the first carries the theorems.

\section{Known Limitations}
\label{sec:limits}

Some of the limits below are the language's: they stay whatever work is put in.
The others are this paper's, and further work could lift them.
Table~\ref{tab:posture} says which instrument holds each rule at build time.

\subsection{Limits of principle}

\paragraph{The compiler does not check a template's body against its constraints.}
Definition checking was the half of the \Cpp{0x} design~\cite{gregor2006concepts} that \Cpp{20} did not take up (Section~\ref{sec:intro}).
So Rules~2 and~3 are posture: they are held outside the compiler, and no tool turns them into the compiler's verdict.

\paragraph{Lookup stops at \cppinline{std}.}
A free function on a type you do not own is found by argument-dependent lookup in that type's namespace, and for \cppinline{std::plus<size_t>} that is \cppinline{std}.
So \cppinline{unit(std::plus<size_t>)} declared after the concept is never found.
Listing~\ref{lst:rule2} declares a deleted primary, which is found by name and specialised.
It puts its one constrained overload, the instance for the unsigned integrals, before the shape, where ordinary lookup sees it.
The same wall makes an operator on \cppinline{std::pair} of standard carriers unreachable from inside \cppinline{std::plus}.
A pair of monoids is a monoid, but not through \cppinline{std::plus<std::pair<A, B>>}, so the former of two operations must be a type of ours.
This is where the translation's ``instance resolution'' and \Cpp{}'s name lookup pull apart.
FJlt resolves it by fiat: an instance is a specialisation of the trait, found by the trait's name.

\paragraph{A typed function object promises what its body cannot keep.}
\cppinline{std::plus<T>} declares its result type as \cppinline{T}, so a shape that asks \cppinline|{ Op{}(a, b) } -> std::same_as<T>| is satisfied for any \cppinline{T}, including one with no \cppinline{+}.
The failure comes later, inside \cppinline{<functional>}, when something evaluates the call.
The transparent \cppinline{std::plus<>} does not have the gap: its result type is \cppinline{decltype(t + u)}, and the shape sees the failure.
It is the body-versus-signature gap of Rule~2 one level down, in the standard library.
The listings avoid it by never asking a typed function object about a carrier it was not written for.

\paragraph{A shape knows the laws someone declared.}
\Cpp{}'s own words are that a type \emph{satisfies} a concept, which the compiler decides, and \emph{models} it, which it does not.
A law is what modelling asks beyond satisfying, and the posture makes it a declared certificate, a specialisation the compiler finds but does not check against the operation.
So \cppinline{false} means \emph{not known}, not \emph{no}: \cppinline{*} on \cppinline{size_t} is commutative, nobody in the listings certifies it, and \cppinline{IsCommutativeMonoid<size_t, multiplies<size_t>>} is refused.
The same declaration is the only refusal available for a carrier that passes a shape by signature and breaks its law by value.
\cppinline{double} under \cppinline{+} has the signature of a monoid, IEEE arithmetic being total, but \cppinline{+} is not associative and the unit law fails at NaN.
Nobody certifies it, and the shape with laws does not have it.

\paragraph{Undefined behaviour has one binding time.}
Constant evaluation refuses undefined behaviour, so a listing that overflows a signed integer does not compile (Table~\ref{tab:binding}).
At runtime the same program does whatever the hardware does.
This is the only way the two evaluations of Theorem~\ref{thm:simulation} can disagree in \Cpp{} where they cannot in FJlt.
The listings close it by using unsigned carriers, whose arithmetic is total.
A signed integer is still a chain under \cppinline{<}, with \cppinline{min} and \cppinline{max} a bounded lattice, but under \cppinline{+} or \cppinline{*} it is no monoid, since overflow is undefined, so no certificate makes it a count's semiring.
A Jlt program on \cppinline{int} is a Jlt program only where its arithmetic cannot overflow, which is a fact about the program that no rule checks.

\paragraph{The compiler has its own limits.}
Table~\ref{tab:binding} lists two, steps and call depth, and the template instantiation depth bounds either binding time, since instantiation precedes both.
They are the compiler's to set, and a program that exceeds one does not compile.
Rule~3 keeps them predictable, because every fold's length is in the program: a budget, or the depth of a term.
A fold over a budget has no recursion and meets no depth limit.
A fold over a typed term, such as the library's \cppinline{cata} over \cppinline{Compose<F, G>}, is one instantiation per nesting, bounded by \texttt{-ftemplate-depth}.
A fold over a term that is a value, evaluated at compile time, is one \cppinline{constexpr} call per nesting, bounded by \texttt{-fconstexpr-depth}.
Raising a limit is a flag, not a change to the program.

\subsection{Limits of this presentation}

\paragraph{The linter reads names.}
Rules~2 and~3 are decidable, so a checker for them is engineering rather than a research problem.
The repository has one, run after the build in its continuous-integration pipeline on the compiler's own front end.
It checks Rule~3 for every body the compiler instantiates, up to the blind spots its rule files document: no loop but the library's iteration primitive, and no function on a call cycle.
It checks Rule~1's syntactic part for the functions the compiler never evaluates: \cppinline{constexpr} and \cppinline{const} where the rule wants them, no state, no result by reference.
It checks Rule~2 at the level of names: a body may use, on a value of parameter type, only what a declared constraint names.
A finding is a breach, or a gap in the linter's reading of the standard's concepts, and is read before it is acted on.
Its silence certifies nothing, since it reads names, not arities or types.
Definition checking proper is work this paper does not promise.
An agentic reviewer reads every pull request against the three rules, with Section~\ref{sec:posture} as its brief, and reaches what the linter does not.
The listings and the library's core are held at zero on all three rules, to the extent the two instruments reach.
The one planted finding is the test's \cppinline{twice_loose}, which adds a value to itself under no constraint.

\paragraph{The adequacy argument covers part of the library.}
Table~\ref{tab:closure} is measured complete for the \texttt{category} module and the listings only.
The modules \texttt{order}, \texttt{sets} and \texttt{relational} are held by the same linter.
A file is gated at zero under a rule once it is clean, and the rest is gated at today's count, a ratchet that only goes down.
What remains there is a run-time layer kept for the Python bindings: heap-allocated term trees, run lists stored in a \cppinline{std::map}, and errors reported by throwing.
Bringing it into the posture is a redesign, not a fix, and is not done here.

\paragraph{Facts live in tables, instances in functions.}
FJlt's instance is a specialisation of a function template, and the listings are written that way.
The library behind them stores its facts in class and variable templates, \cppinline{unit_trait<T, Op>} and \cppinline{is_commutative_v<T, Op>}.
It reads them through the functions the listings use, \cppinline{unit<T>(Op{})} and \cppinline{commutative<T>(Op{})}.
The reason is partial specialisation: ``every \cppinline{Rational<I>} is a monoid under \cppinline{+}'' is one declaration for a family, and only class and variable templates admit it.
A function template cannot be partially specialised.
A constrained overload in its place is found only when it precedes the shape, as Listing~\ref{lst:rule2}'s is, while the library's registrations come after its shapes, in other modules.
So the library writes its registrations in a form the listings do not, which Appendix~\ref{app:fjlt:closure} desugars into the kernel's.
There, a registration over one family is an instance with a context, and a default beside families resolves by specificity (Appendix~\ref{app:fjlt:typing}).

\paragraph{The library is part of the toolchain.}
``Standard \Cpp{23}'' names a language and a library, and the claim holds for a pair of implementations, not for the standard.
\mbox{\cppinline{std::bind_front}} is standard, and the version in one widely used library does not compile under the compiler this paper uses.
The listings were built with one compiler against two standard libraries, and that is what ``compiles as written'' means here.
The youngest piece the posture uses is the fold algorithms over ranges, which entered the standard in 2022 and which the library this paper builds with completed in its release 23~\cite{libcxx2026status}.
An enumeration is not among the listings' counts: \Cpp{23} cannot list an enumeration's enumerators, so its chain would have to be declared enumerator by enumerator, and the static reflection of \Cpp{26} would compute it.

\section{Related Work}
\label{sec:related}

\paragraph{Type classes.}
Dictionary passing is Wadler and Blott's~\cite{wadler1989adhoc}.
Table~\ref{tab:dictionary} is that translation with \Cpp{}'s names in the left column, and the row without a counterpart there, structural satisfaction, is the difference Bernardy et al.~\cite{bernardy2010generic} place at the centre of their comparison of concepts and type classes.
Coherence, that a program has one meaning however its constraints are resolved, is where the designs diverge: Racordon et al.~\cite{racordon2025coherence} survey how Haskell, Swift, Rust and Scala keep or trade it, between unique instances and context-dependent resolution.
FJlt takes the strict side by construction, since an instance is a function specialisation and the one-definition rule admits one per head.
Theorem~\ref{thm:coherence} is that choice stated as a property of the translation, and the price, that instances for families of types declared after their shape do not fit, is in Section~\ref{sec:limits}.
Rust and Swift also check a generic body against its bounds: a comparison on an unconstrained type parameter is a compile error in both, with the missing bound named in the message~\cite{klabnik2023rust,swift2026generics}.
That is Rule~2 as a compiler check, the half \Cpp{20} dropped, and the posture, together with the linter of Section~\ref{sec:limits}, is what recovering it by hand costs.

\paragraph{Concepts, and the calculus next door.}
The nearest neighbour of Appendix~\ref{app:fjlt} is Siek and Lumsdaine's $F^G$~\cite{siek2005essential,siek2004formalization}: System~F with concepts and models, translated into System~F by dictionary passing, with the translation proved sound in Isabelle.
It was written for the concepts then proposed for \Cpp{0x}~\cite{gregor2006concepts,dosreis2006specifying}, which checked template bodies and were removed~\cite{stroustrup2009remove}, leaving the gap Rule~2 names.
$F^G$'s models are nominal and can be declared for whole families of types, which is what the library behind this paper's listings needs after its shapes, where FJlt's function-specialisation instances are not found (Section~\ref{sec:limits}).
FJlt is the smaller calculus, and the price of being a subset of a shipped language.
Garcia et al.~\cite{garcia2007extended} compare eight languages' support for generic programming against a fixed design.
The rows of their table that \Cpp{} lacked at the time, multi-type concepts and retroactive modelling, are the rows Listing~\ref{lst:rule2} exercises with \cppinline{IsMonoid<T, Op>} and specialisations on types one does not own.

\paragraph{Featherweight calculi.}
Featherweight Java~\cite{igarashi2001featherweight} set the pattern: a core calculus small enough to prove things about, with a syntax that is a subset of the host language's.
Its theorems are proved directly, progress and preservation over its own rules, because type soundness of a language with subtyping has no simpler calculus to inherit from.
Featherweight Go~\cite{griesemer2020featherweight} follows the pattern for structural subtyping and monomorphisation, and \emph{Generic Go to Go}~\cite{ellis2022generic} proves a dictionary-passing translation correct by a bisimulation.
That is the genre Section~\ref{sec:guarantees} is in, preservation and simulation of a translation, with soundness, termination and parametricity inherited from the target rather than proved from scratch.

\paragraph{Formal semantics of \Cpp{}.}
CoreC++~\cite{wasserrab2006operational} gives an operational semantics and a machine-checked type safety proof for multiple inheritance; Ramananandro, Dos Reis and Leroy~\cite{ramananandro2011layout,ramananandro2012construction} mechanise object layout, construction and destruction in Coq.
These formalise the part of \Cpp{} that Rule~1 excludes, objects with identity and lifetime, and none covers templates, concepts or constant evaluation, so FJlt is a fragment with its own grammar rather than a subset of a formalised \Cpp{}.

\paragraph{The target.}
Strong normalisation of System~F is Girard's \cite{girard1989proofs}, parametricity Reynolds' \cite{reynolds1983types}, and data types as their own folds B\"ohm and Berarducci's \cite{bohm1985automatic}.
The appendix uses the three as black boxes, which is the point of translating into System~F rather than proving about FJlt directly.

\paragraph{Functional programming in \Cpp{}, and the other direction.}
Functional programming in \Cpp{} is practised and taught: in a book~\cite{cukic2018functional}, in a metaprogramming library~\cite{chagnon2016hana}, and in category theory written in \Cpp{}~\cite{milewski2019category}; none states a fragment or proves anything of it.
The opposite route to the same end verifies a program in a proof assistant and extracts C from it, as Low* does from F*~\cite{protzenko2017verified}; Jlt keeps the programmer in \Cpp{} and puts the proof in the translation.

\paragraph{Coding standards and profiles.}
The documents an audit of \Cpp{} works from are rule catalogues: MISRA \Cpp{}~\cite{misra2023cpp} and the SEI CERT standard~\cite{ballman2016cert} list hundreds of rules, each justified by the defects it prevents, with no statement of what a compliant program computes.
Jlt is narrower, a pure computational core with no I/O, and so complements them rather than replacing them; where they meet they can differ, as MISRA forbids recursion except in constant evaluation and Rule~3 admits structural recursion on the strength of a termination argument.
The nearest relatives are the safety profiles proposed for \Cpp{26}~\cite{sutter2025profiles}, named subsets the compiler would enforce, and the criticism that a profile should come with the invariant it upholds~\cite{muller2025principled}: Jlt reads as a functional profile, and its three rules state theirs.

\paragraph{What is new here.}
Not the translation nor the calculus-with-concepts, but the claim that the shipped language already contains the fragment, with a calculus whose syntax is that \Cpp{}, listings that run under a stock compiler at both binding times, and an adequacy argument that says where the compiler stops checking and the author starts.

\section{Conclusion}
\label{sec:conclusion}

Three rules on standard \Cpp{23} were stated, and a program that keeps them is, up to the gaps Section~\ref{sec:translation:adequacy} names, a term of a core calculus whose syntax is that \Cpp{}.
The calculus translates into System~F by dictionary passing.
The translation preserves types and evaluation and is a function of the program (Theorems~\ref{thm:preservation} to~\ref{thm:coherence}), so a program of the calculus terminates, is parametric and is sound (Corollaries~\ref{cor:termination} to~\ref{cor:soundness}).

What this costs is stated rather than softened.
Two of the three rules are held by the author and not by the compiler, since a template body is checked at instantiation and a loop is not checked for a bound.
A tool in the repository narrows the gap (Section~\ref{sec:limits}).
A fold may run out of budget, and when it does the type says so.
Instances for families of types live in tables and are read through functions, so the library's registrations are sugar, which the appendix desugars, not kernel terms as written.
And ``standard \Cpp{23}'' names a compiler and a library together (Section~\ref{sec:limits}).

Four things follow as work not done here.
Completing the linter into a checker: definition checking proper, over types and arities and the full constraint language, is the distance between the repository's tool (Section~\ref{sec:limits}) and the \Cpp{0x} design, and until it is covered membership in the fragment is a reading the tool narrows, not a verdict it gives.
Certifying that a run-time shortcut agrees with the fold it replaces, which a branch on the binding time leaves to a declared law or to a reader: when a fold over lists can be partitioned and its parts combined is what the third homomorphism theorem characterises~\cite{gibbons1996third}, and a shape could declare it.
A mechanisation of the proofs, as Siek and Lumsdaine did for $F^G$ in Isabelle~\cite{siek2004formalization}, so that the theorems hold as stated rather than in sketch.
And laws that are computed with rather than only declared, which needs terms and their composition.

Nothing was added to the language, the compiler or the library.
What was added is a boundary, inside which a mainstream compiler checks claims of a modest but real kind about programs that then run unchanged.
So the posture needs nothing installed beyond a compiler and nothing at run time beyond what the program already links: it is available wherever a \Cpp{23} compiler is, and its potential users are the people who already write \Cpp{23}, among a community of some 4.5 million \Cpp{} developers in 2020~\cite{stroustrup2020thriving}.
