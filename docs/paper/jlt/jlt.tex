\title{The Juliet Posture: Structurally Typed Functional Programming in Standard \Cpp{23}}
\author{Vincent Kr\"autler}
\date{\today}

\begin{document}
\maketitle

\begin{abstract}
Parametric polymorphism, type classes, structural recursion and algebraic laws are usually associated with languages built for them: Haskell, OCaml, Agda.
We show that they are available in standard \Cpp{23}, with a stock compiler and no extensions.
The vehicle is a fragment of the language we call the \emph{Juliet Posture} ($\mathbf{Jlt}$), defined by three rules: values are \cppinline{std::semiregular} and functions \cppinline{constexpr} and pure; generic code varies with a type only through that type's concepts and traits; and recursion only folds, over a term, a finite carrier or explicit fuel.
Under these rules a \Cpp{} program translates into System~F: concepts and traits by the dictionary-passing translation of type classes, recursion by the fold encoding of data types, so programs in the fragment are parametric and terminate.
A side effect is that one program runs at compile time or at runtime, unchanged.
As a running example, the unit and the laws of a monoid are stated once, as \cppinline{constexpr} functions of the operation, and read twice: by concepts at compile time, by ordinary calls at runtime.
The two readers are the two halves of the dictionary-passing translation, side by side.
The rules are a discipline the compiler does not enforce; we state where the correspondence holds, where it is a translation rather than an isomorphism, and what the fragment gives up.
\end{abstract}

\section{The Posture}
\label{sec:posture}

Jlt is not a dialect and not a library.
It is standard \Cpp{23} under three rules, and a program follows the rules or it does not; the compiler enforces some of them and we say which.
Listing~\ref{lst:posture} shows each rule once.

% Verbatim up to formatting in category/jlt_listings_test.cpp (Rule 2 reuses
% Listing 1's shape).
\begin{listing}[htbp]
\begin{cpp}
static_assert(std::semiregular<size_t>);
static_assert(std::semiregular<std::pair<size_t, bool>>);

constexpr size_t square(size_t x) { return x * x; }

static_assert(square(12) == 144);
\end{cpp}
\begin{cpp}
template <typename T>
constexpr T twice_loose(T x) { return x + x; }

template <typename T, typename Op = std::plus<T>>
  requires IsMonoid<T, Op>
constexpr T twice(T x) { return Op{}(x, x); }

static_assert(twice_loose(std::string{"ab"}) == "abab");
static_assert(twice<size_t>(21) == 42);
\end{cpp}
\begin{cpp}
template <typename T, typename Op = std::plus<T>>
  requires IsMonoid<T, Op>
constexpr T times(T x, size_t n) {
  return std::ranges::fold_left(std::views::repeat(x, n), unit<T>(Op{}), Op{});
}

static_assert(times<size_t>(7, 6) == 42);
\end{cpp}
\caption{The three rules, one panel each.
Rule~1: values are \cppinline{std::semiregular}, functions are \cppinline{constexpr} and pure, so \cppinline{square(12)} is a fact the compiler can check.
Rule~2: \cppinline{twice_loose} varies with \cppinline{T} through an operation no concept named, and compiles for \cppinline{std::string}; \cppinline{twice} names its shape (\cppinline{IsMonoid}, Listing~\ref{lst:monoid}) and is the only one of the two Jlt admits.
Rule~3: recursion only folds, over a range whose length is fixed before it starts; \cppinline{times} folds over \cppinline{n} copies of \cppinline{x}, and this paper contains no loop.}
\label{lst:posture}
\end{listing}

\paragraph{Rule 1: values and pure functions.}
Every type a Jlt program passes around is \cppinline{std::semiregular}: default constructible, copyable, and nothing else is assumed.
Every function is \cppinline{constexpr} and depends on its arguments alone.
What this buys is that a call is a value, with no time attached to it.
The compiler evaluates \cppinline{square(12)} in a \cppinline{static_assert}, and the same function runs at runtime, unchanged; Section~\ref{sec:binding} makes a program out of that.
The compiler enforces the rule in part: a \cppinline{constexpr} function that reaches for state fails to evaluate at compile time, but nothing stops a caller from only ever calling it at runtime.

\paragraph{Rule 2: a type varies behaviour only through its concepts and traits.}
Generic code may do with a \cppinline{T} what \cppinline{T}'s concepts say it can, and nothing else.
\cppinline{twice_loose} breaks the rule: its body uses \cppinline{+}, which no constraint mentions, and so it means whatever \cppinline{+} means at each type, string concatenation included.
\cppinline{twice} keeps it: every operation in the body is one that \cppinline{IsMonoid<T, Op>} names.
What this buys is Section~\ref{sec:translation}: a function that only uses what its constraints name is a function of a record of those operations, and that is a System~F term.
The compiler does not enforce this rule at all.
A template body is checked at instantiation, against the type actually supplied, not at definition, against the constraint; \cppinline{twice_loose} is accepted and so would be a version of \cppinline{twice} that used \cppinline{+} behind its \cppinline{requires} clause.
This is the rule the fragment is named for, and it is a posture: the programmer holds it, the compiler does not.

\paragraph{Rule 3: recursion only folds.}
A Jlt function recurses in one way: \cppinline{std::ranges::fold_left} over a range whose length is fixed before the fold starts, \cppinline{std::views::repeat(x, n)} or \cppinline{std::views::iota(0, n)}.
\cppinline{n} is the fuel, and it is a value the caller supplies before the fold starts; \cppinline{times} folds the monoid's operation over \cppinline{n} copies of \cppinline{x}, starting from its unit.
What is ruled out is the loop whose bound is computed as it goes, and the function that calls itself on an argument it cannot show to be smaller.
What this buys is termination and, with Rule~2, the System~F reading: a fold over \cppinline{repeat(x, n)} is the Church numeral $\overline{n}$ applied to the step, and a fold over \cppinline{iota(0, n)} is primitive recursion, which the numeral builds (Appendix~\ref{app:fjlt:translation}); data as their own folds is the reading of B\"ohm and Berarducci~\cite{bohm1985automatic}.
What it costs is that some programs cannot say \emph{yes} or \emph{no} and must say \emph{out of fuel}; Section~\ref{sec:binding} shows the price being paid.
The compiler enforces the rule only at compile time, where an evaluation that does not finish hits the step limit; at runtime a \cppinline{while (true)} compiles like any other loop, which is why this paper contains none: the one loop is inside \cppinline{std::ranges::fold_left}, and every function composes.

Two remarks on scope.
The rules are checked at the level of this paper's listings, each of which compiles as written, not at the level of a library; Section~\ref{sec:limits} says what else in the surrounding code the rules do not reach.
And the rules are a subset by discipline, not by tooling: a Jlt program is a \Cpp{23} program, built by a stock compiler with no flags beyond \texttt{-std=c++23}, and the appendix makes the subset precise.

\subsection{One shape, two monoids}
\label{sec:translation:example}

Here is the whole translation in one shape.
A monoid is a carrier with an associative operation and a unit for it.
Listing~\ref{lst:monoid} states that shape once, as a concept over a carrier \cppinline{T} and an operation \cppinline{Op}, and then populates it: \cppinline{bool} has it twice, \cppinline{size_t} four times.

% Verbatim in src/test/cpp/modules/dedekind/category/jlt_listings_test.cpp,
% which also checks that the tree's unit<T>(Op{}) and laws agree.
\begin{listing}[htbp]
\begin{cpp}
template <typename T, typename Op> constexpr T unit(Op) = delete;

template <typename T, typename Op>
concept IsMonoid = std::semiregular<T> && requires(const T a, const T b) {
  { Op{}(a, b) } -> std::same_as<T>;
  { unit<T>(Op{}) } -> std::same_as<T>;
};

template <typename T, typename Op = std::plus<T>>
  requires IsMonoid<T, Op>
constexpr T twice(T x) { return Op{}(x, x); }
\end{cpp}
\begin{cpp}
template <> constexpr bool unit<bool>(std::logical_and<bool>) { return true; }
template <> constexpr bool unit<bool>(std::logical_or<bool>) { return false; }

static_assert( IsMonoid<bool, std::logical_and<bool>>);
static_assert( IsMonoid<bool, std::logical_or<bool>>);
static_assert(!IsMonoid<bool, std::plus<bool>>);
\end{cpp}
\begin{cpp}
template <> constexpr size_t unit<size_t>(std::plus<size_t>) { return 0; }
template <> constexpr size_t unit<size_t>(std::multiplies<size_t>) { return 1; }
template <> constexpr size_t unit<size_t>(std::bit_or<size_t>) { return 0; }
template <> constexpr size_t unit<size_t>(std::bit_and<size_t>) {
  return SIZE_MAX;
}

static_assert(IsMonoid<size_t, std::plus<size_t>>);
static_assert(IsMonoid<size_t, std::multiplies<size_t>>);
static_assert(IsMonoid<size_t, std::bit_or<size_t>>);
static_assert(IsMonoid<size_t, std::bit_and<size_t>>);

static_assert(twice<size_t>(21) == 42);
static_assert(twice<size_t, std::multiplies<size_t>>(21) == 441);
\end{cpp}
\begin{minted}{text}
MonoidDict T Op  =  { unit : T,  op : T → T → T }
and_bool  =  { unit = true,  op = λa. λb. a ∧ b }
plus_u64  =  { unit = 0,     op = λa. λb. a + b }
twice     =  Λ T. Λ Op. λ d : MonoidDict T Op. λ x : T.  d.op x x
twice [u64] [plus] plus_u64 21
\end{minted}
\caption{The monoid shape, populated.
Top: \cppinline{unit}, a function of the operation at a carrier, declared and deleted; the shape, with one requirement the compiler reads off the carrier and one it reads from \cppinline{unit}; a function over the shape.
Middle: \cppinline{bool} is a monoid under $\land$ and $\lor$, and not under \cppinline{+}, which yields an \cppinline{int}.
Then \cppinline{size_t} under $+$, $\cdot$, $|$ and $\&$, and \cppinline{twice} at two of them.
Bottom: the same in System~F.
The shape is a record type, each specialisation of \cppinline{unit} is a record, of which two are shown, and the function takes the record as a parameter.
The operation is part of the index, so one carrier has several monoids, and nobody wrote a struct for any of them.}
\label{lst:monoid}
\end{listing}

The bottom panel reads the other three as a System~F program.
The concept is a record type, one field per requirement.
A \cppinline{requires} clause on a function is one more parameter, the record.
A call passes the record, and the compiler finds the record to pass.
That is dictionary passing, the translation of type classes into System~F,\footnote{Wadler and Blott~\cite{wadler1989adhoc}; the record is their dictionary.} and Table~\ref{tab:dictionary} names the \Cpp{} devices it meets.
Two of them deserve a sentence each.
\cppinline{Op} is a type with exactly one value, the closure \cppinline{Op{}}, so under translation the type \emph{is} that closure, and \cppinline{Op{}(a, b)} is \texttt{d.op a b}.
And a unit is a choice.
The compiler can see that \cppinline{size_t} has a \cppinline{+}, but not which element is neutral for it, so someone states the fact, once, as a specialisation of \cppinline{unit}.
An instance declaration in a type-class system is the same act; here it is a specialisation, and the one-definition rule makes sure there is one.
The primary is declared and deleted rather than left out, for a reason worth a footnote.\footnote{A plain overload \cppinline{unit(std::plus<size_t>)} beside the concept is never found: inside the concept, \cppinline{unit<T>(Op{})} is looked up by argument-dependent lookup in the namespace of \cppinline{Op}, which is \cppinline{std}, not ours.
The deleted primary is found by name, and its specialisations with it.
A call to the primary itself is a substitution failure, so an operation nobody registered is rejected, not silently accepted.
Section~\ref{sec:limits} lists this wall.}
\cppinline{unit} is a value-level function, so the fact is also visible at runtime, where \cppinline{unit<size_t>(op)} is an ordinary call; Section~\ref{sec:binding} uses this.

The operation being part of the index is a small thing with a payoff.
A class indexed by the carrier alone gives one carrier one monoid, and the second monoid needs a wrapper type.\footnote{\texttt{Sum} and \texttt{Product} in Haskell's base library.}
Here \cppinline{IsMonoid<T, Op>} is a relation between a carrier and an operation, and the six \cppinline{static_assert}s of Listing~\ref{lst:monoid} are six of its witnesses at two carriers.
The defaulted \cppinline{Op} picks the additive reading when a caller does not care.

\subsection{Shapes compose by conjunction}
\label{sec:translation:semiring}

A semiring is two monoids on one carrier, with laws tying them together: addition commutes, multiplication distributes over it.
Listing~\ref{lst:semiring} states the laws the same way Listing~\ref{lst:monoid} stated the unit, as functions of the operation, and then states the shape as a conjunction and finds three semirings among the monoids we have.

% Verbatim in jlt_listings_test.cpp (as Listing 1).
\begin{listing}[htbp]
\begin{cpp}
template <typename T, typename Op> constexpr bool commutative(Op) = delete;
template <typename T, typename Mul, typename Add>
constexpr bool distributive(Mul, Add) = delete;

template <typename T, typename Op>
concept IsCommutativeMonoid = IsMonoid<T, Op> && commutative<T>(Op{});

template <typename T, typename Add, typename Mul>
concept IsSemiring = IsCommutativeMonoid<T, Add> && IsMonoid<T, Mul> &&
                     distributive<T>(Mul{}, Add{});
\end{cpp}
\begin{cpp}
template <>
constexpr bool commutative<size_t>(std::plus<size_t>) { return true; }
template <>
constexpr bool commutative<size_t>(std::bit_or<size_t>) { return true; }
template <>
constexpr bool commutative<bool>(std::logical_or<bool>) { return true; }
template <>
constexpr bool distributive<size_t>(std::multiplies<size_t>, std::plus<size_t>) {
  return true;
}
template <>
constexpr bool distributive<size_t>(std::bit_and<size_t>, std::bit_or<size_t>) {
  return true;
}
template <>
constexpr bool distributive<bool>(std::logical_and<bool>,
                                  std::logical_or<bool>) {
  return true;
}

static_assert( IsSemiring<size_t, std::plus<size_t>, std::multiplies<size_t>>);
static_assert( IsSemiring<size_t, std::bit_or<size_t>, std::bit_and<size_t>>);
static_assert( IsSemiring<bool, std::logical_or<bool>, std::logical_and<bool>>);
static_assert(!IsCommutativeMonoid<size_t, std::multiplies<size_t>>);
\end{cpp}
\caption{Laws as functions of the operation, and the semiring shape as a conjunction.
Top: two laws, declared and deleted, and the two shapes that require them.
Bottom: six certificates, and three semirings: $(\mathbb{Z}/2^{64}, +, \cdot)$, the bit vectors $(\mathbb{B}^{64}, |, \&)$ and $(\mathbb{B}, \lor, \land)$.
The last line is a fact about the listing, not about multiplication: nobody certified it commutative, so the shape does not know it.}
\label{lst:semiring}
\end{listing}

Two kinds of requirement went into these verdicts.
Structural ones the compiler reads off the type: that \cppinline{a + b} is a \cppinline{size_t}, or that \cppinline{true + true} is not a \cppinline{bool}.
Declared ones a specialisation records: the units, and now the laws.
Both are requirements of the same shape, and both become fields of the same record; a law is a field of type \texttt{Bool}, and the conjunction is a product, \texttt{SemiringDict T Add Mul = MonoidDict T Add × MonoidDict T Mul × Bool × \ldots}, so a conjunct that is itself a shape becomes a field holding a record, which is how a superclass is passed.

One thing the listing does not do, and cannot.
A concept checks signatures.
It sees that \cppinline{Add} and \cppinline{Mul} exist on \cppinline{T} with the right types, and that a unit is declared for each.
It cannot see that \cppinline{Mul} distributes over \cppinline{Add}, and nothing in the listing checks the certificate against the operation.
\cppinline{distributive<T>(Mul{}, Add{})} is not a fact the compiler decides; it is a fact someone states, like the unit, and the last \cppinline{static_assert} shows the price: a true law nobody stated is a law the shape does not have.
Section~\ref{sec:limits} says what this leaves to the author.
The shape permits \cppinline{unit<T>(Add{}) == unit<T>(Mul{})}, as a semiring should; the one-element carrier witnesses it.

\subsection{Instances with contexts}
\label{sec:translation:contexts}

One rule remains.
An instance may itself require instances: the unit of a pair is the pair of units, provided both components have one.
In \Cpp{} that is a generic function with a \cppinline{requires} clause, and the clause is the context.
Under translation it is a function from the components' records to the composite's:
\begin{minted}{text}
pair_unit  =  Λ A. Λ B. λ da : MonoidDict A OpA. λ db : MonoidDict B OpB.
                (da.unit, db.unit)
\end{minted}
The compiler applies such functions outside in, as often as the composite nests, and the recursion ends because a context can only mention proper parts of the type it is for.\footnote{The termination conditions on instance contexts are studied by Sulzmann et al.~\cite{sulzmann2007understanding}; GHC calls them the Paterson conditions.
The FJlt syntax enforces them by construction, since a context can only mention the type arguments of the operation being specialised.}

\subsection{What the translation guarantees}
\label{sec:translation:theorems}

Three theorems and three corollaries, stated in Section~\ref{sec:guarantees} once the running example has shown what they are good for, and proved in sketch in Appendix~\ref{app:fjlt:theorems}: the translation preserves types, it preserves evaluation, and it is a function of the program (coherence); consequently every Jlt program terminates, every generic Jlt function is parametric, and well-typed programs evaluate to values.

\subsection{From \Cpp{} to the calculus}
\label{sec:translation:adequacy}

The theorems are about FJlt.
For them to say anything about a \Cpp{} program, two things have to hold, and they hold in different ways.

\emph{Every FJlt program is a \Cpp{23} program, with the same meaning.}
This direction is by construction.
The grammar of Figure~\ref{fig:fjlt-syntax} is a subset of the \Cpp{} grammar, written in \Cpp{}'s own spelling, and FJlt's evaluation is \Cpp{}'s constant evaluation restricted to that subset.
The argument is a walk over the productions: a concept is a concept, an explicit specialisation is one, a call with explicit type arguments is one, and in each case the \Cpp{} standard's rule for the construct is the FJlt rule.
Two places in that walk deserve a sentence.
Constant evaluation refuses undefined behaviour, signed overflow included, so an FJlt program evaluated at compile time cannot go wrong silently; at runtime it can, which is why the listings' carriers are unsigned, and why \cppinline{int} appears in this paper only as a counter-example.
And the standard library pieces the grammar admits, \cppinline{std::pair}, the function objects and the concepts, are taken with their standard meaning, so the argument depends on the library being correct in the same way every \Cpp{} program does.

\emph{A \Cpp{} program that follows the three rules is an FJlt program.}
This direction is not a theorem, because the compiler does not check it, and the point of Rule~2 is exactly the part it does not check.
Table~\ref{tab:adequacy} lists what \Cpp{} has and FJlt does not, and how each is kept out.

Five of the seven rows are closed by the grammar or by constant evaluation: a program that uses them is not accepted, or not accepted at compile time.
The two that remain are Rule~2 and Rule~3, and they are posture.
A template body that uses an operation its constraints do not name compiles anyway, as \cppinline{twice_loose} did; a loop whose bound changes as it runs compiles anyway.
Whether a body obeys Rule~2 is decidable by inspection of the body against its \cppinline{requires} clause, which is the definition checking that the \Cpp{0x} concepts design included~\cite{gregor2006concepts} and the shipped feature does not~\cite{stroustrup2009remove}, so a tool could close the gap; we have not written one, and this paper's listings are checked by reading.
Rule~3 is likewise checkable for the loop forms the grammar admits.

So the theorems transfer to a \Cpp{} program on two conditions: that it is written in the subset, which the compiler checks, and that its generic bodies and loops keep to the two rules the compiler does not, which the author checks.
Section~\ref{sec:limits} is the list of places where the first condition is harder to meet than it looks.

\section{Two Binding Times}
\label{sec:binding}

Every function in this paper has run twice already.
\cppinline{square(12)}, \cppinline{twice<size_t>(21)} and \cppinline{unit<size_t>(std::plus<size_t>{})} were each checked in a \cppinline{static_assert}, and the test behind the listings calls the same functions at runtime on values it did not have at compile time.
Rule~1 is what makes that unremarkable: a \cppinline{constexpr} function of its arguments alone has no binding time of its own, and Theorem~\ref{thm:simulation} says the two evaluations agree.
The interesting case is the fold, because fuel can arrive at either time.
Listing~\ref{lst:fuel} searches the naturals for the first one with a property, under a budget it may run out of.

% Verbatim up to formatting in jlt_listings_test.cpp, which also calls
% first with a fuel it did not have at compile time.
\begin{listing}[htbp]
\begin{cpp}
template <typename P>
constexpr std::pair<size_t, bool> advance(std::pair<size_t, bool> s, size_t i) {
  return s.second ? s : std::pair{i, P{}(i)};
}

template <typename P>
constexpr std::optional<size_t> first(size_t fuel) {
  std::pair<size_t, bool> s =
      std::ranges::fold_left(std::views::iota(size_t{0}, fuel),
                             std::pair{size_t{0}, false}, advance<P>);
  return s.second ? std::optional{s.first} : std::nullopt;
}

struct Over1000 {
  constexpr bool operator()(size_t n) const { return n * n > 1000; }
};

static_assert(first<Over1000>(40) == 32);
static_assert(!first<Over1000>(30));
\end{cpp}
\caption{Fuel, and running out of it.
\cppinline{advance} is one step on a state (the candidate, whether it has the property), frozen once it has; the property is a type, \cppinline{Over1000}, as the operations of Section~\ref{sec:translation} are.
\cppinline{first} folds it over the first \cppinline{fuel} naturals and reads the state out: the candidate if one was found, \cppinline{std::nullopt} if the budget ended first.
The second \cppinline{static_assert} is not "no square exceeds 1000"; it is "none among the first 30".}
\label{lst:fuel}
\end{listing}

\paragraph{The answer when fuel runs out is an absence.}
Whether some natural has a given property is, for a general property, not something a fuel can be replaced by a proof of, and a function that searches has to say what it says when the budget ends first.
In Jlt the type says it: \cppinline{std::optional<size_t>}, with \cppinline{std::nullopt} for \emph{the budget ended}, which is neither \emph{yes} nor \emph{no}.\footnote{It is not a third truth value either; a predicate that can run out of fuel answers in \cppinline{optional<bool>}, three values that mean \emph{no}, \emph{yes}, and \emph{not within the budget}.}
That is the whole price of Rule~3, and it is paid in the type rather than in a crash or a hang: a caller that forgets the third case does not compile.

\paragraph{Fuel at compile time is the same fuel.}
\cppinline{first<Over1000>(40)} is a constant, so the compiler evaluates it; \cppinline{first<Over1000>(fuel)} with \cppinline{fuel} read from input is the same function, and the test behind the listing calls it so.
Nothing about the fold changes between the two: at compile time the compiler runs \cppinline{fold_left}, at runtime the processor does, and the range it folds is a lazy \cppinline{iota} in both cases.
The compiler has a fuel of its own, a limit on the steps a constant evaluation may take, and Rule~3 keeps a program from ever meeting it by accident, since every loop's length is in the program's hands.

\paragraph{Why not a generator.}
\Cpp{23} has a second way to iterate without committing to a container, \cppinline{std::generator} with \cppinline{co_yield}, and it is the natural reflex for a bounded computation that should not allocate.
It does not fit here, for three reasons that are the three rules.
A coroutine cannot be \cppinline{constexpr}, so it has one binding time; its frame is mutable state; and it is an unfold, a producer of a stream that something else must stop, where Rule~3 wants the stopping in the program.
What a generator is good for, a stream consumed lazily at runtime, is exactly what the rule forbids unless something bounds the consumption, and in the standard library that something is \cppinline{std::views::take(n)}: the fuel again, under another name.\footnote{The library behind this paper has the \cppinline{constexpr} version of the generator: a \cppinline{Path<T>} is a lazy stream $\mathbb{N} \to T$, \cppinline{iterate(seed, step)} builds one, and \cppinline{.at(n)} reads it at fuel $n$.}

\section{Guarantees}
\label{sec:guarantees}
% The three theorems about the translation of Section~\ref{sec:translation}
% and Appendix~\ref{app:fjlt}, stated after the exhibits so that each can
% point at one.  Proof sketches in Appendix~\ref{app:fjlt:theorems}; the
% adequacy argument (C++ -> FJlt) is Section~\ref{sec:translation:adequacy}
% and is not a theorem.

Write $P$ for an FJlt program and $\llbracket P \rrbracket$ for its translation into System~F.
One word on what the theorems rest on.
Their proofs (Appendix~\ref{app:fjlt:theorems}) are inductions over the grammar, the typing and the translation of FJlt, and never mention the three rules.
The rules are not the hypotheses of the theorems; they are what makes a \Cpp{} program a term of the calculus the theorems are about, and that step is the argument of Section~\ref{sec:translation:adequacy}.

\begin{theorem}[Type preservation]
\label{thm:preservation}
If $\Gamma \vdash e : \tau$ in FJlt, then $\llbracket \Gamma \rrbracket \vdash \llbracket e \rrbracket : \llbracket \tau \rrbracket$ in System~F.
\end{theorem}

A well-formed FJlt program translates to a well-typed term.
Each \cppinline{requires} clause has become a record parameter, and at each call the instance the compiler resolved supplies a record of the type that parameter demands.

\begin{theorem}[Simulation]
\label{thm:simulation}
If $e$ evaluates to $v$ in FJlt, then $\llbracket e \rrbracket$ reduces to $\llbracket v \rrbracket$ in System~F, and for closed terms of base type the converse holds.
\end{theorem}

What a \cppinline{static_assert} sees is what the translation computes, and, by Rule~1, what the runtime computes; Section~\ref{sec:binding} is this theorem run twice.

\begin{theorem}[Coherence]
\label{thm:coherence}
The translation is a function of the program: two resolutions of the same constraint at the same concrete types yield the same record.
\end{theorem}

In \Cpp{} this is overload resolution together with the one-definition rule: at concrete types a specialisation is unique, or the program is ill-formed.
It is what makes "the unit of \cppinline{+} at \cppinline{size_t}" a phrase with one meaning in the whole program, and therefore something a law can be stated about.

\begin{corollary}[Termination]
\label{cor:termination}
Every FJlt program terminates.
\end{corollary}

By Theorem~\ref{thm:simulation} and strong normalisation of System~F~\cite{girard1989proofs}.
Fuel in Rule~3 is therefore not a guard against non-termination; it is how a bound is said.

\begin{corollary}[Parametricity]
\label{cor:parametricity}
A generic FJlt function satisfies the free theorem of its System~F type.
\end{corollary}

By Theorem~\ref{thm:preservation} and Reynolds' abstraction theorem~\cite{reynolds1983types}.
\cppinline{twice} at a monoid can only combine its argument with itself by \cppinline{op}.
It is also why an instance with a context (Section~\ref{sec:translation:contexts}) can read a composite's law off its components' records: the composite cannot do anything the components' records do not provide.

\begin{corollary}[Type soundness]
\label{cor:soundness}
A well-typed closed FJlt term of base type evaluates to a value.
\end{corollary}

This is the theorem a reader of Featherweight Java~\cite{igarashi2001featherweight} expects first, and here it comes last, because it is inherited: the term's image is well-typed (Theorem~\ref{thm:preservation}) and so reduces to a normal form, which at a base type is a constant, and the converse half of Theorem~\ref{thm:simulation} carries that constant back.
Featherweight Java has to prove progress and preservation over its own rules; a translation imports them.

All six are claims about FJlt.
What they say about a \Cpp{} program is mediated by the adequacy argument of Section~\ref{sec:translation:adequacy}, which is an argument and not a theorem, and the next section says where it is thin.

\label{sec:limits}

Everything in this section was met while writing the listings, and each item is a place where "standard \Cpp{23} under three rules" is thinner than the sentence sounds.

\paragraph{The two rules the compiler does not check.}
Section~\ref{sec:translation:adequacy} said it: Rules~2 and~3 are posture.
A template body is checked against the type it is instantiated at, not against its \cppinline{requires} clause, so \cppinline{twice_loose} compiles; a loop is not checked for a bound, so \cppinline{while (true)} compiles.
Both are decidable by inspection, and the first is the definition checking that the \Cpp{0x} concepts design included and \Cpp{20} dropped, so a checker is a tool rather than a research problem; we have not written one, and this paper's listings are checked by reading and by a test that compiles and runs them.
Rule~3 the paper keeps trivially, by having no loop at all: the one it needs is \cppinline{std::ranges::fold_left}'s.

\paragraph{Lookup stops at \cppinline{std}.}
A free function on a type you do not own is found by argument-dependent lookup in that type's namespace, and for \cppinline{std::plus<size_t>} that is \cppinline{std}.
So \cppinline{unit(std::plus<size_t>)} declared beside the concept is never found, and Listing~\ref{lst:monoid} declares a deleted primary instead, which is found by name and specialised.
The same wall makes an operator on \cppinline{std::pair} of standard carriers unreachable from inside \cppinline{std::plus}: a pair of monoids is a monoid, but not through \cppinline{std::plus<std::pair<A, B>>}, which is why the former of two operations must be a type of ours.
This is the one place the translation's "instance resolution" and \Cpp{}'s name lookup pull apart, and FJlt resolves it by fiat: an instance is a specialisation of the trait, found by the trait's name, and nothing else.

\paragraph{A typed function object promises what its body cannot keep.}
\cppinline{std::plus<T>} declares its result type as \cppinline{T}, so a shape that asks \cppinline|{ Op{}(a, b) } -> std::same_as<T>| is satisfied for any \cppinline{T}, including one with no \cppinline{+}; the failure comes later, inside \cppinline{<functional>}, when something evaluates the call.
The transparent \cppinline{std::plus<>} is honest, since its result type is \cppinline{decltype(t + u)} and the shape sees the failure.
It is the body-versus-signature gap of Rule~2 one level down, in the standard library, and the listings avoid it by never asking a typed function object about a carrier it was not written for.

\paragraph{Facts live in tables, instances in functions.}
FJlt's instance is a specialisation of a function template, and the listings are written that way.
The library behind them stores its facts in class and variable templates, \cppinline{unit_trait<T, Op>} and \cppinline{is_commutative_v<T, Op>}, and reads them through the functions the listings use, \cppinline{unit<T>(Op{})} and \cppinline{commutative<T>(Op{})}.
The reason is partial specialisation: "every \cppinline{Rational<I>} is a monoid under \cppinline{+}" is one declaration for a family, and only class and variable templates admit it; a function template cannot be partially specialised, and an overload in its place runs into the lookup wall above.
So the library is FJlt at its reads and not at its registrations, and the adequacy argument covers the listings, not the library.
Closing the gap would mean a resolution mechanism for families that is found by name, which \Cpp{} does not have; the honest statement is that FJlt's instance resolution is a subset of what the library needs.

\paragraph{The library is part of the toolchain.}
"Standard \Cpp{23}" names a language and a library, and the claim holds for a pair of implementations, not for the standard.
\cppinline{std::bind_front} is standard, and the version in one widely used library does not compile under the compiler this paper uses; the listing that used it now uses a fold instead.
The listings were built with one compiler against two standard libraries, and that is what "compiles as written" means here.

\paragraph{The compiler has its own fuel.}
Constant evaluation is bounded by a step limit the compiler sets, and a program that exhausts it fails to compile.
Rule~3 is what keeps that limit out of the picture: every fold's length is in the program's hands, so the program, not the compiler, decides what is too long, and the limit is a knob to raise rather than a wall to hit.
Template instantiation depth is a second such knob; the listings are nowhere near either.

\paragraph{Undefined behaviour has one binding time.}
Constant evaluation refuses undefined behaviour, so a listing that overflows a signed integer does not compile; at runtime the same program does whatever the hardware does.
This is the one way the two evaluations of Theorem~\ref{thm:simulation} can disagree in \Cpp{} where they cannot in FJlt, and the listings close it by using unsigned carriers, whose arithmetic is total.
A Jlt program on \cppinline{int} is a Jlt program only where its arithmetic cannot overflow, which is a fact about the program that no rule checks.

\section{Related Work}
\label{sec:related}

\paragraph{Type classes.}
Dictionary passing is Wadler and Blott's~\cite{wadler1989adhoc}: a class is a record type, an instance a record, a constraint a parameter, and a constrained call passes the record the compiler resolved.
Table~\ref{tab:dictionary} is that translation with \Cpp{}'s names in the left column, and the one row without a counterpart there, structural satisfaction, is the difference Bernardy et al.~\cite{bernardy2010generic} place at the centre of their comparison of concepts and type classes.

\paragraph{Concepts, and the calculus next door.}
The nearest neighbour of Appendix~\ref{app:fjlt} is Siek and Lumsdaine's $F^G$~\cite{siek2005essential,siek2004formalization}: System~F with concepts and models, translated into System~F by dictionary passing, with the translation proved sound in Isabelle.
It was written for the concepts then proposed for \Cpp{0x}~\cite{gregor2006concepts,dosreis2006specifying}, which checked template bodies against their constraints; those concepts were removed in 2009~\cite{stroustrup2009remove}, and the feature that shipped in \Cpp{20} checks uses and not definitions, which is the gap Rule~2 names.
$F^G$'s models are nominal and can be declared for whole families of types, which is what the library behind this paper's listings needs and FJlt's function-specialisation instances do not provide (Section~\ref{sec:limits}); FJlt is the smaller calculus, and the price of being a subset of a shipped language.
Garcia et al.~\cite{garcia2007extended} compare eight languages' support for generic programming against a fixed design; the rows of their table that \Cpp{} lacked at the time, multi-type concepts and retroactive modelling, are the rows Listing~\ref{lst:monoid} exercises with \cppinline{IsMonoid<T, Op>} and specialisations on types one does not own.

\paragraph{Featherweight calculi.}
Featherweight Java~\cite{igarashi2001featherweight} set the pattern: a core calculus small enough to prove things about, with a syntax that is a subset of the host language's.
Its theorems are proved directly, progress and preservation over its own rules, because type soundness of a language with subtyping has no simpler calculus to inherit from.
Featherweight Go~\cite{griesemer2020featherweight} follows the pattern for structural subtyping and monomorphisation, and \emph{Generic Go to Go}~\cite{ellis2022generic} proves a dictionary-passing translation correct by a bisimulation; that is the genre Section~\ref{sec:guarantees} is in, preservation and simulation of a translation, with soundness, termination and parametricity inherited from the target rather than proved from scratch.

\paragraph{Formal semantics of \Cpp{}.}
CoreC++~\cite{wasserrab2006operational} gives an operational semantics and a machine-checked type safety proof for multiple inheritance; Ramananandro, Dos Reis and Leroy~\cite{ramananandro2011layout,ramananandro2012construction} mechanise object layout, construction and destruction in Coq.
These formalise the part of \Cpp{} that Rule~1 excludes, objects with identity and lifetime, and none covers templates, concepts or constant evaluation, which is why FJlt is a fragment with its own grammar rather than a subset of a formalised \Cpp{}.

\paragraph{The target.}
Strong normalisation of System~F is Girard's~\cite{girard1989proofs}, parametricity Reynolds'~\cite{reynolds1983types}, and data types as their own folds B\"ohm and Berarducci's~\cite{bohm1985automatic}; the appendix uses the three as black boxes, which is the point of translating into System~F rather than proving about FJlt directly.

\paragraph{What is new here.}
Not the translation, which is Wadler and Blott's, nor the calculus-with-concepts, which is $F^G$'s.
What is new is the claim that the shipped language already contains the fragment: three rules on standard \Cpp{23}, a core calculus whose syntax is that \Cpp{} and whose listings compile and run under a stock compiler at both binding times, an adequacy argument that says where the compiler stops checking and the author starts, and a list of the seams met on the way.
