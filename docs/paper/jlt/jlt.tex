\begin{abstract}
Parametric polymorphism, type classes and structural recursion are the tools with which a functional programmer says what a program does and has a type checker hold it to that.
By contrast, \Cpp{23} is a mainstream multi-paradigm language in which functional programming is one style among many.
It runs much of machine learning and most embedded devices, holds zero-overhead abstraction as a design principle, and its current standard has the material: compile-time evaluation of ordinary functions and of most of the standard library, concepts, and folds over ranges.
It does not, however, hold a generic function to its declared constraints: the body may use any operation its type argument happens to have.

This paper characterizes a fragment of \Cpp{23} as it ships, an embedded language whose programs are ordinary \Cpp{23} programs, which translates into System~F and compiles into conventional executables.
The fragment is type-class-style code subject to three rules, which we call the Juliet Posture (Jlt):
i) values are copyable data and functions are pure and evaluable at compile time;
ii) generic code varies with a type only through that type's concepts and traits;
iii) recursion is bounded: it only folds, over finite data or over a time budget.

A core calculus, Featherweight Jlt, is presented.
Its syntax is a subset of Jlt as written, and it translates into System~F, the polymorphic lambda calculus that Haskell's type classes translate into.
Concepts are turned into record types, trait specialisations into records, constraints into parameters, and folds become the iterators of inductive types.
The translation preserves types, preserves evaluation and is a function of the program, so a program of the calculus terminates, is parametric and evaluates to a value.
Algebraic invariants such as the associativity and the unit of a monoid are then values of the program.
They are stated once and read either by concepts at compile time or by function calls at run time.
Evidence that the calculus holds real programs and that the translation is total on it: a) proof sketches in the appendix; b) the listings, which compile and run under a stock compiler at both binding times, by a test in the public repository; c) a library whose core is held to the rules by a mechanical checker; d) the compiled output, without the scaffolding.

What the System~F image has, termination, parametricity and a value, the Jlt program inherits: by theorem for the calculus and by an adequacy argument for the executable.
What is gained is a mainstream compiler that checks claims of a modest but real kind, at compile time, where checking is cheap, about programs that then run unchanged.
Jlt simplifies the trade between a functional style and a mainstream systems language in both directions.
The correctness guarantees of the style are checked at compile time.
The performance and the ecosystem of the host language remain available at run time.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The case for functional programming has been made the same way for decades, and it is a good case.
A function that depends on its arguments alone can be replaced by its value: programs can be read as equations, rewritten by them, and reasoned about by them~\cite{hughes1989why}.
A function that is polymorphic in a type cannot inspect that type, so its type alone says a great deal about what it does~\cite{wadler1989theorems}.
A class of types with operations and laws, Haskell's type classes, lets generic code be written once against the operations and reasoned about by the laws~\cite{wadler1989adhoc}.
The case is usually made in a language built around it, and that is where this paper departs: it makes the case in standard \Cpp{23}, with a stock compiler and no extensions.

Two things make \Cpp{} the right place to make it now.
The first is where \Cpp{} is: much of machine learning and most embedded devices run on it, and a growing number of the people who write it arrive from Python with a functional vocabulary and less sense of how much of it the language already supports.
The second is that the standard keeps evolving, and this paper draws the boundary in the most recent one.
\Cpp{23}, as a stock compiler implements it, evaluates ordinary functions and most of its standard library at compile time, constrains templates with concepts, and folds over ranges.
The posture uses nothing else.
One decision in that evolution matters here.
Concepts as proposed for \Cpp{0x} checked a template's definition against its constraints~\cite{gregor2006concepts,dosreis2006specifying}; concepts as standardised in \Cpp{20} check its uses~\cite{stroustrup2009remove}, so a constrained body may use operations its constraints do not name, and that is the gap Rule~2 fills.
The designers named the problem at the outset, in 2003: ``crucial aspects of the programmer's understanding of a template cannot be expressed directly in the code for compilers and other tools to use''~\cite{stroustrup2003concepts}.
The language therefore contains the material for a typed functional fragment but does not enforce its boundary.
The question this paper answers is what discipline draws the boundary, and what a program inside it is.

The answer is a fragment we call the \emph{Juliet Posture}, or Jlt: the discipline of restricting oneself to the part of \Cpp{23} that reads as System~F.
It is an embedded language in Hudak's sense~\cite{hudak1996building}: its programs are ordinary \Cpp{23} programs, type-checked and compiled by the host, and its domain is no narrower than typed functional programming.
The name is structural typing's~\cite{pierce2002tapl,cardelli1996typesystems}: a type is known by what it does and not by what it is called, a rose by any other name~\cite{shakespeare1597romeo}.
That is how a concept admits a type, and how the fragment admits a carrier.
It has three rules.
Values are \cppinline{std::semiregular} and functions are \cppinline{constexpr} and pure.
Generic code varies with a type only through that type's concepts and traits.
Recursion only folds, over finite data or over a time budget.
Under these rules a program written in the grammar of a small calculus translates into System~F by dictionary passing: concepts become record types, trait specialisations records, constraints parameters.
It inherits what System~F guarantees: termination, parametricity and a value.
"Posture" is the honest word: the compiler enforces some of the rules and not others, and Table~\ref{tab:posture} says which.

There is a reason to care about the checked part beyond taste: a check is worth something whenever the author is not the one trusted, a machine writing the code, or a code base audited against a policy.
The last few years have shown what a formal system with a checker is worth once machines write in it: proofs in Lean~\cite{demoura2021lean} found by learned search are accepted because the checker, not the author, says so~\cite{hubert2025olympiad}.
\Cpp{} is not a theorem prover.
But under the posture its compiler does check something of the same kind: a \cppinline{static_assert} on a \cppinline{constexpr} function is a claim the compiler verifies, a concept is a claim about a type the compiler decides, and the same program runs unchanged at runtime, so what was checked once is what executes.
What the compiler checks is membership in the fragment, and the guarantees follow from membership: correct by construction in Dijkstra's sense~\cite{dijkstra1976discipline}, for a modest notion of correct.
A discipline that makes a mainstream compiler into a checker of this modest sort is worth stating precisely, and that is what the calculus in the appendix is for.

What the posture is for, in a library written in it, is code that reads as combinators and runs as the compiler's pre-computation of them: pretty because the structure lives in the combinators, fast because the compiler can reason about them and evaluate at build time what does not depend on run-time input.
Section~\ref{sec:binding} shows the mechanism on one function.

The paper is written for \Cpp{} programmers first, with System~F as the warranty; for researchers who want the performance and portability of \Cpp{} without being software engineers, and who will take a guard rail; and for readers of programming languages who want to know what a shipped language already contains.

\section{From \Cpp{} to Jlt}
\label{sec:posture}

Jlt is not a dialect and not a library.
It is standard \Cpp{23} under three rules, and a program follows the rules or it does not. The compiler enforces some of them and we say which.
Each rule has a listing of a few lines, verbatim in the test that holds this paper's listings, up to formatting and to repetitions a comment elides.

Two names are kept apart in what follows.
Jlt is the posture, and a Jlt program is a \Cpp{} program that keeps the three rules.
Featherweight Jlt, FJlt, is the calculus of Appendix~\ref{app:fjlt}, a grammar with typing, evaluation and a translation into System~F, and the theorems of Section~\ref{sec:guarantees} are about FJlt alone.
Every FJlt program is a Jlt program by construction; that a Jlt program is an FJlt program when it is written in the calculus's grammar is the adequacy argument of Section~\ref{sec:translation:adequacy}, which is what lets the theorems reach a \Cpp{} program, and Section~\ref{sec:limits} says what keeps the rules and is still outside the grammar.

\paragraph{Rule 1: values and pure functions.}
Every type a Jlt program passes around is \cppinline{std::semiregular}: default constructible, copyable, and nothing else is assumed.
Every function is \cppinline{constexpr} and depends on its arguments alone.\footnote{A \cppinline{constexpr} function may still change its own locals: constant evaluation permits modifying only objects whose lifetime began within it, so no mutation can leak, which is the encapsulated state of \cppinline{runST}~\cite{launchbury1994lazy}.
At runtime the checker of Section~\ref{sec:limits} holds the body to the same condition by closing each channel a mutation could leak through: parameters, results, the object, statics, globals, \cppinline{volatile}, boxes, and escaping closures that capture by reference.}

\begin{listing}[htbp]
\begin{minipage}[t]{0.66\linewidth}
\begin{cpp}
static_assert(std::semiregular<size_t>);
static_assert(std::semiregular<std::pair<size_t, bool>>);

template <std::semiregular T>
constexpr T id(const T& x) { return x; }

static_assert(id(size_t{42}) == 42);
\end{cpp}
\end{minipage}\hfill
\begin{minipage}[t]{0.32\linewidth}
\begin{minted}{llvm}
define i64 @id_rt() {
  ret i64 42
}
\end{minted}
\end{minipage}
\caption{Rule~1: the identity arrow, and what a call of it compiles to.
\cppinline{T} is a value, \cppinline{const T&} denotes it, and it comes back by value. \cppinline{id(42)} is a fact the compiler checks.
Beside it, the same call at runtime, \cppinline{size_t id_rt() { return id(size_t{42}); }}, is the constant: its LLVM IR under Clang 23 at \texttt{-O2}, attributes stripped.}
\label{lst:rule1}
\end{listing}

Listing~\ref{lst:rule1} is the rule in one function.
\cppinline{id} takes a \cppinline{const T&} and returns a \cppinline{T}: the reference denotes the value, nothing can change the value through it, so what comes back is what was passed, and a parameter written \cppinline{const T} or \cppinline{const T&} is one and the same parameter, the second an optimisation the translation erases.
An object a function could change would be state, which the rule excludes. The shapes' requirements say \cppinline{const T a} for that reason, and \cppinline{const}-correctness is the rule written on the type.
Two consequences keep the identification exact.
A function returns a value, never a reference, since a reference into an argument could outlive a temporary the caller passed; and every member function is \cppinline{const}, since a non-\cppinline{const} one changes its object.
The grammar of Appendix~\ref{app:fjlt} has neither a reference type nor a non-\cppinline{const} member, so the checker of Section~\ref{sec:limits} enforces on \Cpp{} what the calculus assumes.
A function passed as an argument is a value like any other, and its \cppinline{const} call operator observes rather than changes.
What this buys is that a call is a value, with no time attached to it.
The compiler evaluates \cppinline{id(size_t{42})} in a \cppinline{static_assert}, and the same function runs at runtime, unchanged, where the panel of Listing~\ref{lst:rule1} is all that is left of the call: the value, returned. Section~\ref{sec:binding} makes a program out of that.
The compiler enforces the rule in part: a \cppinline{constexpr} function that reaches for state fails to evaluate at compile time, but nothing stops a caller from only ever calling it at runtime.\footnote{Boxed values on the heap such as \cppinline{std::shared_ptr<const T>} require special treatment, as there are two heaps with non-overlapping life cycles: the one the running program has at runtime, and the one the compiler simulates while it evaluates a \cppinline{constexpr} function during compilation.
They are values in the sense of this section on two conditions, that the pointee is \cppinline{const} and that nothing asks which box it is. In practice, support for evaluating them at compile time is absent in \Cpp{23} and arrives with \Cpp{26}~\cite{keir2025constexprsharedptr}.}

\paragraph{Rule 2: a type varies behaviour only through its concepts and traits.}
Generic code may do with a \cppinline{T} what \cppinline{T}'s concepts say it can, and nothing else.

\begin{listing}[htbp]
\begin{minipage}[t]{0.48\linewidth}
\begin{cpp}
template <typename T, typename Op>
constexpr T unit(Op) = delete;

template <typename T, typename Op>
constexpr bool associative(Op) = delete;

template <std::unsigned_integral T>
constexpr T unit(std::plus<T>) { return 0; }
template <std::unsigned_integral T>
constexpr bool associative(std::plus<T>) {
  return true;
}

template <typename T, typename Op>
concept IsMonoid =
    std::semiregular<T> &&
    requires(const T a, const T b) {
      { Op{}(a, b) } -> std::same_as<T>;
      { unit<T>(Op{}) } -> std::same_as<T>;
    } && associative<T>(Op{});

template <typename T>
concept IsMonoidPlus =
    IsMonoid<T, std::plus<T>> &&
    requires(const T a, const T b) {
      { a + b } -> std::same_as<T>;
    };
\end{cpp}
\end{minipage}\hfill
\begin{minipage}[t]{0.48\linewidth}
\begin{cpp}
template <>
constexpr std::string unit<std::string>(
    std::plus<std::string>) {
  return {};
}
template <>
constexpr bool associative<std::string>(
    std::plus<std::string>) {
  return true;
}

template <IsMonoidPlus T>
constexpr T twice(T x) { return x + x; }

static_assert(twice<size_t>(21) == 42);
static_assert(
    twice(std::string{"ab"}) == "abab");
\end{cpp}
\end{minipage}
\caption{Rule~2: a shape, its instances, and a function of it.
Left: the monoid shape, with one requirement the compiler reads off the carrier, \cppinline{Op{}(a, b)}, one it reads from \cppinline{unit}, a trait declared and deleted, and one law, associativity, declared the same way; before the shape, an instance for every unsigned integral under \cppinline{+}, a constrained overload, which has to precede the shape to be found (Section~\ref{sec:limits}); \cppinline{IsMonoidPlus} is the shape with \cppinline{Op} fixed to \cppinline{std::plus<T>}, naming the operator the standard defines \cppinline{plus} by, \cppinline{a + b}.
Right: \cppinline{std::string} registered as a monoid under \cppinline{+}, the empty string its unit, and \cppinline{twice}, whose body is \cppinline{x + x}, at \cppinline{size_t} and at \cppinline{std::string}.}
\label{lst:rule2}
\end{listing}

The breach is Listing~\ref{lst:rule2}'s \cppinline{twice} without its clause, \cppinline{template <typename T> constexpr T twice_loose(T x) { return x + x; }}, kept in the test as a planted finding: its \cppinline{+} means whatever \cppinline{+} means at each type, and that string concatenation is a monoid is luck, not a declaration.
\cppinline{twice} keeps the rule with the same body: \cppinline{IsMonoidPlus<T>} names \cppinline{a + b}, the unit and the law, so \cppinline{x + x} is a requirement of the constraint read at \cppinline{a, b := x}, the difference between the two functions is the clause, and strings pass it the moment someone registers their unit, the empty string, as the right panel does.
What this buys is Section~\ref{sec:translation}: a function that only uses what its constraints name is a function of a record of those operations, and that is a System~F term.
A template body is checked at instantiation, against the type actually supplied, not at definition, against the constraint. \cppinline{twice_loose} is accepted, and so would be a \cppinline{twice} whose clause did not name \cppinline{+}.
This is the rule the fragment is named for, and it is a posture: the programmer holds it, the compiler does not.

\paragraph{Rule 3: recursion only folds.}
A Jlt program is finite for one of two reasons, and Rule~3 admits those two.
Either it folds over \emph{finite data}: a term, which is a finite composition of finitely many nodes, folded by \cppinline{cata}, or a contiguous interval of a finite chain, \cppinline{chain_view{lo, hi}}, folded by \cppinline{std::ranges::fold_left}, with \cppinline{std::views::iota(0, n)} the interval on \cppinline{size_t}.
Or it iterates a step over \emph{a time budget}: a standard fold, such as \cppinline{fold_left}, over \cppinline{std::views::repeat(x, n)}, where \cppinline{n} is a value the caller supplies before the fold starts.

\begin{listing}[htbp]
\begin{cpp}
template <typename T, typename Op = std::plus<T>>
  requires IsMonoid<T, Op>
constexpr T times(T x, size_t n) {
  return std::ranges::fold_left(std::views::repeat(x, n), unit<T>(Op{}), Op{});
}

static_assert(times<size_t>(7, 6) == 42);
\end{cpp}
\caption{Rule~3: a fold over a budget.
\cppinline{times} folds the operation over \cppinline{n} copies of \cppinline{x}, starting from the unit.}
\label{lst:rule3}
\end{listing}

Listing~\ref{lst:rule3}'s \cppinline{times} is the second kind: the monoid's operation folded over \cppinline{n} copies of \cppinline{x}, starting from its unit. What the processor runs of it is one multiplication, with the fold, the unit and the record gone, and Section~\ref{sec:binding} says why.
What this buys is termination and, with Rule~2, the System~F reading: both kinds are catamorphisms, of the term's inductive type in the first case and of a finite prefix of $\mathbb{N}$ in the second, and a fold over an interval is the second read on the interval's length (Appendix~\ref{app:fjlt:translation}). Data as their own folds is the reading of B\"ohm and Berarducci~\cite{bohm1985automatic}.
What it costs is that some programs cannot say \emph{yes} or \emph{no} and must say \emph{out of budget}. Section~\ref{sec:binding} shows the price being paid.
The compiler enforces the rule only at compile time, where an evaluation that does not finish hits the step limit. At runtime a \cppinline{while (true)} compiles like any other loop.
This paper contains none: its loops are inside \cppinline{fold_left} and \cppinline{cata}, and every function composes.

\section{From Featherweight Jlt to System~F}
\label{sec:translation}
% Establishes: what a reader must believe about the System F reading, by one
% example and the rules it uses.  The full calculus (Appendix~\ref{app:fjlt})
% is the warranty; a reader who stops here knows the claims and their cost.

This section is about one map, the translation $\llbracket \cdot \rrbracket$ from Featherweight Jlt, the subset of \Cpp{23} that Appendix~\ref{app:fjlt:syntax} writes down as a grammar, into System~F with records and the iterators of inductive types.
A concept becomes a record type, an instance a record, a constraint a parameter and a fold an iterator. Appendix~\ref{app:fjlt:translation} defines the map in full.
The map is total on FJlt: every FJlt program has an image, and Section~\ref{sec:guarantees} says what the image guarantees.
It is partial on \Cpp{}: a \Cpp{} program is an FJlt program only when it keeps the three rules, and Section~\ref{sec:translation:adequacy} is the argument for when it does.
Everything the listings do is covered by six of its rules, which Table~\ref{tab:rules} states, the rest being bookkeeping.
Read the table with Listings~\ref{lst:rule2} and~\ref{lst:monoid} beside it: \cppinline{IsMonoid} is the first row, \cppinline{unit<bool>(std::logical_and<bool>)} the third, the instance for the unsigned integrals and \cppinline{twice} the fourth and \cppinline{twice}'s \cppinline{static_assert}s the fifth.

\subsection{One shape, two monoids}
\label{sec:translation:example}

Listing~\ref{lst:rule2} stated the monoid shape. Listing~\ref{lst:monoid} populates it at \cppinline{bool} and reads both as a System~F program.
The concept is a record type, one field per requirement, a law a field of type \texttt{Bool}.
A \cppinline{requires} clause on a function is one more parameter, the record, and a call passes the record the compiler resolved.
That is dictionary passing, the translation of type classes into System~F,\footnote{Wadler and Blott~\cite{wadler1989adhoc}. The record is their dictionary.} and Table~\ref{tab:dictionary} names the \Cpp{} devices it meets.
\cppinline{Op} is a type with exactly one value, the closure \cppinline{Op{}}, so under translation the type \emph{is} that closure, and \cppinline{Op{}(a, b)} is \texttt{d.op a b}.
A unit is a choice: the compiler can see that \cppinline{size_t} has a \cppinline{+}, but not which element is neutral for it, so someone states the fact once, as a specialisation of \cppinline{unit}, which is an instance declaration in a type-class system, and the one-definition rule makes sure there is one.
The primary is declared and deleted so that its specialisations are found by its name, since an overload beside the concept is found only when it precedes it (Section~\ref{sec:limits}).
A law is stated the same way, as \cppinline{associative} is, and Listing~\ref{lst:rule2}'s instance for every unsigned integral is an instance with a context, the function from records to a record of Section~\ref{sec:translation:contexts}.

\subsection{Shapes compose by conjunction}
\label{sec:translation:semiring}

A semiring is two monoids on one carrier, with laws tying them together: addition commutes, multiplication distributes over it.
Listing~\ref{lst:semiring} states the laws the same way Listing~\ref{lst:rule2} stated the unit and associativity, as functions of the operation, and then states the shape as a conjunction and finds three semirings, and two distributive lattices among them.

% Verbatim in jlt_listings_test.cpp.
\begin{listing}[htbp]
\begin{cpp}
template <typename T, typename Op> constexpr bool commutative(Op) = delete;
template <typename T, typename Mul, typename Add>

template <typename T, typename Op>
concept IsCommutativeMonoid = IsMonoid<T, Op> && commutative<T>(Op{});

template <typename T, typename Add, typename Mul>
concept IsSemiring = IsCommutativeMonoid<T, Add> && IsMonoid<T, Mul> &&
                     distributive<T>(Mul{}, Add{});
\end{cpp}

The fourth line is a fact about the listing, not about multiplication: nobody certified it commutative, so the shape does not know it.
The last is refused for a law that is false, \cppinline{+} is not idempotent, and for one that is merely undeclared, \cppinline{*} commutative, and the shape does not tell the two apart: \cppinline{false} means \emph{not known}, not \emph{no}.}

Two kinds of requirement went into these verdicts.
Structural ones the compiler reads off the type: that \cppinline{a + b} is a \cppinline{size_t}, or that \cppinline{std::plus<>} on two \cppinline{bool}s yields an \cppinline{int} and not a \cppinline{bool}.
Declared ones a specialisation records: the units and associativity, and now two more laws.
\Cpp{}'s own words for the two are that a type \emph{satisfies} a concept, which the compiler decides, and \emph{models} it, which it does not. A law is what modelling asks beyond satisfying, and the fragment makes it a declared field.
Both are requirements of the same shape, and both become fields of the same record.
A law is a field of type \texttt{Bool}, and the conjunction is a product, \texttt{SemiringDict T Add Mul = MonoidDict T Add × MonoidDict T Mul × Bool × \ldots}, so a conjunct that is itself a shape becomes a field holding a record, which is how a superclass is passed.

One thing the listing does not do, and cannot.
A concept checks signatures.
It sees that \cppinline{Add} and \cppinline{Mul} exist on \cppinline{T} with the right types, and that a unit is declared for each.
It cannot see that \cppinline{Mul} distributes over \cppinline{Add}, and nothing in the listing checks the certificate against the operation.
\cppinline{distributive<T>(Mul{}, Add{})} is not a fact the compiler decides. It is a fact someone states, like the unit, and the fourth \cppinline{static_assert} shows the price: a true law nobody stated is a law the shape does not have.
The same declaration is the only refusal available for a carrier that passes the shape by type and breaks the law by value: \cppinline{double} is a monoid under \cppinline{+} as far as a signature can see, IEEE arithmetic being total, but \cppinline{+} is not associative and \cppinline{NaN + 0 == NaN} is false, so the unit law fails at NaN.
Nobody certifies it, and the shape with laws does not have it.
Section~\ref{sec:limits} says what this leaves to the author.
The shape permits \cppinline{unit<T>(Add{}) == unit<T>(Mul{})}, as a semiring should. The one-element carrier witnesses it.

\subsection{Instances with contexts}
\label{sec:translation:contexts}

An instance may itself require instances: the unit of a pair is the pair of units, provided both components have one, and Listing~\ref{lst:rule2}'s instance for the unsigned integrals is the simplest case, one context on one carrier.
In \Cpp{} that is a generic function with a \cppinline{requires} clause, and the clause is the context.
Under translation it is a function from the components' records to the composite's:
\begin{minted}{text}
pair_unit  =  Λ A. Λ B. λ da : MonoidDict A OpA. λ db : MonoidDict B OpB.
                (da.unit, db.unit)
\end{minted}
The compiler applies such functions outside in, as often as the composite nests, and the recursion ends because a context can only mention proper parts of the type it is for.\footnote{The termination conditions on instance contexts are studied by Sulzmann et al.~\cite{sulzmann2007understanding}; GHC calls them the Paterson conditions.
The FJlt syntax enforces them by construction, since a context can only mention the type arguments of the operation being specialised.}

\section{Partial Evaluation at Build Time}
\label{sec:binding}

Every function in this paper has run twice already.
\cppinline{id(size_t{42})}, \cppinline{twice<size_t>(21)} and \cppinline{unit<size_t>(std::plus<size_t>{})} were each checked in a \cppinline{static_assert}, and the test behind the listings calls the same functions at runtime on values it did not have at compile time.
Rule~1 is what makes that unremarkable: a \cppinline{constexpr} function of its arguments alone has no binding time of its own, and Theorem~\ref{thm:simulation} says the two evaluations agree.
Both are partial evaluation at build time: the compiler evaluates what it can and leaves the processor the rest, which is nothing for a \cppinline{static_assert}, whose arguments are constants, and for \cppinline{first<Over1000>(budget)} everything but the loop over the budget it does not know.
There is no magic in this.
A program has two moments at which work can be done, build time and run time, and work moves between them: what is pre-computed at the first is not computed at the second, and an abstraction whose cost is paid entirely at the first costs nothing at the second.
The interesting case is the fold, because a budget can arrive at either time.
Listing~\ref{lst:fuel} searches the naturals for the first one with a property, under a budget it may run out of.

% Verbatim up to formatting in jlt_listings_test.cpp, which also calls
% first with a budget it did not have at compile time.
\begin{listing}[htbp]
\begin{cpp}
template <typename P>
concept IsPredicate = std::semiregular<P> && requires(const P p, size_t n) {
  { p(n) } -> std::same_as<bool>;
};

template <IsPredicate P>
constexpr std::pair<size_t, bool> advance(std::pair<size_t, bool> s, size_t i) {
  return s.second ? s : std::pair{i, P{}(i)};
}

constexpr std::optional<size_t> found(std::pair<size_t, bool> s) {
  return s.second ? std::optional{s.first} : std::nullopt;
}

template <IsPredicate P>
constexpr std::optional<size_t> first(size_t budget) {
  return found(std::ranges::fold_left(std::views::iota(size_t{0}, budget),
                                      std::pair{size_t{0}, false}, advance<P>));
}

struct Over1000 {
  constexpr bool operator()(size_t n) const { return n * n > 1000; }
};

static_assert(first<Over1000>(40) == 32);
static_assert(!first<Over1000>(30));

static_assert(std::ranges::fold_left(chain_view{size_t{3}, size_t{5}}, size_t{0},
                                     std::plus<size_t>{}) == 12);

using Negation = NegationArrow<Boole>;
static_assert(monotone(cata(LawAlgebra<>{}, Compose<Negation, Negation>{})) ==
              Ternary::True);
static_assert(IsMonotone<Compose<Negation, Negation>>);
\end{cpp}
\caption{A budget, and running out of it.
\cppinline{advance} is one step on a state (the candidate, whether it has the property), frozen once it has. The property is a type, \cppinline{Over1000}, with a shape, \cppinline{IsPredicate}, as the operations of Section~\ref{sec:translation} are, and Rule~2 is why the shape is there.
\cppinline{first} folds it over the first \cppinline{budget} naturals and \cppinline{found} reads the state out: the candidate if one was found, \cppinline{std::nullopt} if the budget ended first.
The second \cppinline{static_assert} is not "no square exceeds 1000". It is "none among the first 30".
The next line folds over a contiguous interval of a finite chain, \cppinline{chain_view{lo, hi}} from the library, which is what \cppinline{iota(0, n)} is on \cppinline{size_t}.
The last two lines are Rule~3's other kind, a fold over a term, with \cppinline{Negation} the library's negation arrow on $\mathbb{B}$. The paragraph on folds over finite data reads them.}
\label{lst:fuel}
\end{listing}

\paragraph{The answer when the budget runs out is an absence.}
For a general property no budget can be replaced by a proof, so a function that searches has to say what it says when the budget ends first.
In Jlt the type says it: \cppinline{std::optional<size_t>}, with \cppinline{std::nullopt} for \emph{the budget ended}, which is neither \emph{yes} nor \emph{no}.\footnote{It is not a third truth value either. A predicate that can run out of budget answers in \cppinline{optional<bool>}, three values that mean \emph{no}, \emph{yes}, and \emph{not within the budget}.}
That is the price of Rule~3, and it is paid in the type rather than in a crash or a hang: exhaustion is explicit in the result, a caller has to check for it, and what cannot happen is that the budget's end passes unseen as a value of the result type.

\paragraph{A budget at compile time is the same budget.}
\cppinline{first<Over1000>(40)} is a constant, so the compiler evaluates it. \cppinline{first<Over1000>(budget)} with \cppinline{budget} read from input is the same function, and the test behind the listing calls it so.
Nothing about the fold changes between the two: at compile time the compiler runs \cppinline{fold_left}, at runtime the processor does, and the range it folds is a lazy \cppinline{iota} in both cases.
What the processor runs is what the compiler leaves after instantiation and constant folding: \cppinline{id(size_t{42})} is the constant, as the panel of Listing~\ref{lst:rule1} shows, \cppinline{times<size_t>(x, n)} with \cppinline{plus} is one multiplication, \cppinline{x * n}.
The search is a loop of 84 instructions, unrolled by four and without a branch in its body. Appendix~\ref{app:fjlt:ssa} shows the loop before unrolling, with the fold's state as its $\phi$-nodes.
The records of Section~\ref{sec:translation} and the ranges of this section are gone, as Section~\ref{sec:translation:adequacy} said they would be. The discipline costs nothing at runtime, which is the zero-overhead principle~\cite{stroustrup2005abstraction} met by pre-computation: the records' cost is paid at build time, where it is paid once.

\paragraph{Folds over finite data.}
The last three lines of Listing~\ref{lst:fuel} are Rule~3's first kind.
\cppinline{chain_view{lo, hi}} is the contiguous interval of a finite chain, walked by its covering step, of which \cppinline{iota(0, n)} is the instance on \cppinline{size_t}, so the two folds above it and this one are one production of the grammar.
\cppinline{cata} folds the term $\neg \circ \neg$ with the algebra that computes the laws of a function, and \cppinline{monotone} reads one law off the result, in $K_3$, finding it \cppinline{True} since antitone after antitone is monotone.
The concept \cppinline{IsMonotone} on the same term agrees, as it must: the concept and the predicate read one registration, which the library defines on \cppinline{Compose} by the same algebra the fold runs.

\section{From System~F Back to Featherweight Jlt}
\label{sec:guarantees}
% The three theorems about the translation of Section~\ref{sec:translation}
% and Appendix~\ref{app:fjlt}, stated after the exhibits so that each can
% point at one.  Proof sketches in Appendix~\ref{app:fjlt:theorems}; the
% adequacy argument (C++ -> FJlt) is Section~\ref{sec:translation:adequacy}
% and is not a theorem.

The theorems rest on FJlt alone.
Their proofs (Appendix~\ref{app:fjlt:theorems}) are inductions over the grammar, the typing and the translation of FJlt, and never mention the three rules.
The rules are not the hypotheses of the theorems; they are what makes a \Cpp{} program a term of the calculus the theorems are about, and that step is the argument of Section~\ref{sec:translation:adequacy}.

\begin{theorem}[Type preservation]
\label{thm:preservation}
If $\Gamma \vdash e : \tau$ in FJlt, then $\llbracket \Gamma \rrbracket \vdash \llbracket e \rrbracket : \llbracket \tau \rrbracket$ in System~F.
\end{theorem}

A well-formed FJlt program translates to a well-typed term.
Each \cppinline{requires} clause has become a record parameter, and at each call the instance the compiler resolved supplies a record of the type that parameter demands.

\begin{theorem}[Simulation]
\label{thm:simulation}
If $e \longrightarrow e'$ in FJlt, then $\llbracket e \rrbracket \longrightarrow^{+} \llbracket e' \rrbracket$ in System~F, and values translate to values. For closed terms of base type, $e$ evaluates to $v$ if and only if $\llbracket e \rrbracket$ reduces to $\llbracket v \rrbracket$.
\end{theorem}

What a \cppinline{static_assert} sees is what the translation computes, and, by Rule~1, what the runtime computes. Section~\ref{sec:binding} is this theorem run twice.
It is also the notion of equality here, and a notion has to be chosen, since equational reasoning presupposes one and which one is a question of its own~\cite{mazur2008equal}: two closed terms of a carrier are equal when they evaluate to the same value, equality by behaviour and not by identity, and Leibniz's law, that equal arguments give equal results, holds by substitution.\footnote{Leibniz stated it as the identity of indiscernibles and its converse~\cite{leibniz1686discourse}: two things are the same exactly when nothing tells them apart, and the direction a program needs is that equals cannot be told apart by any operation.
In a programming language the law is referential transparency~\cite{strachey2000fundamental}, and a language where $a = b$ but $f(a) \neq f(b)$ for some $f$ has an equality one cannot reason with.}
That choice is what lets Rule~1 ask \cppinline{std::semiregular} and not \cppinline{std::regular}.
No \cppinline{==} is asked of a value: a carrier's \cppinline{==} is one more operation of its signature where it exists, and a function object, a value under Rule~1, has none, which equality by behaviour accommodates and equality by \cppinline{==} would not.
It is this fragment's answer to the question, not a settlement of it.

\begin{theorem}[Coherence]
\label{thm:coherence}
The translation is a function of the program: two resolutions of the same constraint at the same concrete types yield the same record.
\end{theorem}

In \Cpp{} this is overload resolution together with the one-definition rule: at concrete types a specialisation is unique, or the program is ill-formed.
It is what makes "the unit of \cppinline{+} at \cppinline{size_t}" a phrase with one meaning in a program, and therefore something a law can be stated about.

\begin{corollary}[Termination]
\label{cor:termination}
Every FJlt program terminates.
\end{corollary}

By Theorem~\ref{thm:simulation} and strong normalisation of the target~\cite{girard1989proofs}: every step of the program is at least one step of its image, and the image cannot step forever.
The budget in Rule~3 is therefore not a guard against non-termination. It is how a bound is said.

\begin{corollary}[Parametricity]
\label{cor:parametricity}
A generic FJlt function satisfies the free theorem of its System~F type.
\end{corollary}

By Theorem~\ref{thm:preservation} and Reynolds' abstraction theorem~\cite{reynolds1983types}.
\cppinline{twice} at a monoid can only combine its argument with itself by \cppinline{op}.
It is also why an instance with a context (Section~\ref{sec:translation:contexts}) can read a composite's law off its components' records: the composite cannot do anything the components' records do not provide.

\begin{corollary}[Type soundness]
\label{cor:soundness}
A well-typed closed FJlt term of base type evaluates to a value.
\end{corollary}

This is the theorem a reader of Featherweight Java~\cite{igarashi2001featherweight} expects first. It comes last because it is cheap once the rest is in place: a closed well-typed term is a value or takes a step (progress, Lemma~\ref{lem:progress}), and it cannot step forever (Corollary~\ref{cor:termination}), so it reaches a value.
Featherweight Java proves progress and preservation over its own rules too. What the translation adds is the second half of Theorem~\ref{thm:simulation}, that the value reached is the value the System~F image computes.

All six are claims about FJlt.
What they say about a Jlt program is the adequacy argument of the next section, and Section~\ref{sec:limits} says where it is thin.

\section{From Jlt to Featherweight Jlt}
\label{sec:translation:adequacy}

The theorems are about FJlt.
For them to say anything about a \Cpp{} program, two things have to hold, and they hold in different ways.

\emph{Every FJlt program is a Jlt program, with the same meaning.}
This direction is by construction, and Appendix~\ref{app:fjlt:syntax} states it: the grammar of Figure~\ref{fig:fjlt-syntax} is \Cpp{} syntax, FJlt's evaluation is constant evaluation restricted to it, and for each construct the standard's rule is the FJlt rule.
Two places need a word.
Constant evaluation refuses undefined behaviour, signed overflow included, so an FJlt program evaluated at compile time cannot go wrong silently. At runtime it can, and that is the reason the listings' carriers are unsigned and \cppinline{int} appears in this paper only as a counter-example.
And the standard library pieces the grammar admits, \cppinline{std::pair}, the function objects and the concepts, are taken with their standard meaning, so the argument depends on the library being correct in the same way every \Cpp{} program does.

\emph{A Jlt program written in the grammar of Figure~\ref{fig:fjlt-syntax} is an FJlt program.}
This direction is not a theorem, because the compiler does not check two of the rules, and it is conditional on the grammar, because \Cpp{} has what FJlt does not and a Jlt program may use it.
Table~\ref{tab:adequacy} lists what \Cpp{} has, what keeps it out, and what FJlt has instead.

Four of the eight rows are closed by the grammar or by constant evaluation: a program that uses them is not accepted, or not accepted at compile time.

The last row is where the grammar is narrower than the library: its programs branch on a trait or a concept, fold over parameter packs, pass lambdas and case on sums.
We conjecture that each elaborates into FJlt with its meaning kept: a branch on a law as \texttt{?:}, a branch on a concept as specialisation, resolved as instances are, a pack as one instance per arity used, a lambda as an operation struct.
Sums are the narrowest gap: the grammar has the former, \cppinline{optional<T>} is $1 + T$, and its introductions, and lacks the case form, so a program can build an optional and not look inside it.
A sum would enter as a range does, by conditions, two injections and a case; \cppinline{std::variant} is one instance, and the library's \cppinline{IsCoproduct} is that condition written down.
The one point that is not sugar is resolution between two generic functions whose heads both match, which the library's family instances need and FJlt's no-overlap condition forbids.
The elaboration is not written, and until it is the adequacy argument covers the listings and not the library (Section~\ref{sec:limits}).

\Cpp{} does not pass dictionaries, so the translation is a model of what a constrained call means, not of what the compiler emits.
What the compiler does is instantiate: \cppinline{twice<size_t>} is compiled as a separate function with \cppinline{size_t} substituted and every trait call resolved, which in the model is the term $\llbracket \mathit{twice} \rrbracket\,[\mathtt{size\_t}]\,d$ with its type and record arguments applied and $\beta$-reduced before the program runs.
Instantiation is partial evaluation of the dictionary-passing term at a static type, so the two agree on every closed term (that is Theorem~\ref{thm:simulation} read at the binding time where the records are constants), and nothing of a record survives to runtime.
Section~\ref{sec:binding} shows the instruction the compiler is left with, and Appendix~\ref{app:fjlt:ssa} follows the term one step further, into the compiler's own intermediate representation, static single assignment form, a functional language too, as Appel put it~\cite{appel1998ssa}, with the fold's state as the parameters of a loop.
What the model is for is the term \emph{before} that evaluation: parametricity is a property of $\Lambda\alpha.\,\lambda d.\,\ldots$, and it holds of every instantiation because each one is an application of that term.
The two translations, dictionary passing and monomorphisation, are studied side by side for Go by Ellis et al.~\cite{ellis2022generic}, who prove them to agree; \Cpp{} only ever does the second, and the first carries the theorems.

So the theorems transfer to a \Cpp{} program on two conditions: that it is written in the subset, which the compiler checks, and that its generic bodies and loops keep to the two rules the compiler does not, which the author checks.
Section~\ref{sec:limits} is the list of places where the first condition is harder to meet than it looks.

\section{Known Limitations}
\label{sec:limits}

The paragraphs below name practical limitations encountered while stress-testing Jlt. Table~\ref{tab:posture} says which instrument holds each rule at build time, and the first paragraph says how.

\paragraph{The two rules the compiler does not check.}
Section~\ref{sec:translation:adequacy} said it: Rules~2 and~3 are posture, and Table~\ref{tab:posture} says who holds what.
Both are decidable by inspection, so a checker is a tool rather than a research problem, and the repository has one, run after the build in its continuous-integration pipeline on the compiler's own front end.
Rule~3 it checks mechanically, for every body the compiler instantiates and up to the blind spots its rule files document: no loop but the library's iteration primitive and no function on a call cycle, so recursion runs over a term's type or not at all.
Rule~1's syntactic part it checks with it, for the functions the compiler never evaluates: \cppinline{constexpr} and \cppinline{const} where the rule wants them, no state, no result by reference.
Rule~2 is harder, which Table~\ref{tab:adequacy} records as \emph{by reading}.
The tool checks it at the level of names: a body may use on a value of parameter type only what a declared constraint names.
A finding of that check is a breach or a gap in the tool's reading of the standard's concepts, and is read before it is acted on. Its silence certifies nothing, since it reads names, not arities or types.
Definition checking proper, the half the \Cpp{0x} design had~\cite{gregor2006concepts}, is work this paper does not promise.
The rest is reading, and reading too is in the pipeline: an agentic reviewer reads every pull request against the three rules, with Section~\ref{sec:posture} as its brief, reaching what the tool does not.
The listings and the library's core are held at zero on all three rules to the extent the two instruments reach, with one planted finding, the \cppinline{twice_loose} of Section~\ref{sec:posture}; so the listings are checked by the tool, by reading, and by a test that compiles and runs them.

\paragraph{Lookup stops at \cppinline{std}.}
A free function on a type you do not own is found by argument-dependent lookup in that type's namespace, and for \cppinline{std::plus<size_t>} that is \cppinline{std}.
So \cppinline{unit(std::plus<size_t>)} declared after the concept is never found. Listing~\ref{lst:rule2} declares a deleted primary, which is found by name and specialised, and puts its one constrained overload, the instance for the unsigned integrals, before the shape, where ordinary lookup sees it.
The same wall makes an operator on \cppinline{std::pair} of standard carriers unreachable from inside \cppinline{std::plus}: a pair of monoids is a monoid, but not through \cppinline{std::plus<std::pair<A, B>>}, so the former of two operations must be a type of ours.
This is where the translation's "instance resolution" and \Cpp{}'s name lookup pull apart, and FJlt resolves it by fiat: an instance is a specialisation of the trait, found by the trait's name.

\paragraph{A typed function object promises what its body cannot keep.}
\cppinline{std::plus<T>} declares its result type as \cppinline{T}, so a shape that asks \cppinline|{ Op{}(a, b) } -> std::same_as<T>| is satisfied for any \cppinline{T}, including one with no \cppinline{+}. The failure comes later, inside \cppinline{<functional>}, when something evaluates the call.
The transparent \cppinline{std::plus<>} does not: its result type is \cppinline{decltype(t + u)}, and the shape sees the failure.
It is the body-versus-signature gap of Rule~2 one level down, in the standard library, and the listings avoid it by never asking a typed function object about a carrier it was not written for.

\paragraph{Facts live in tables, instances in functions.}
FJlt's instance is a specialisation of a function template, and the listings are written that way.
The library behind them stores its facts in class and variable templates, \cppinline{unit_trait<T, Op>} and \cppinline{is_commutative_v<T, Op>}, and reads them through the functions the listings use, \cppinline{unit<T>(Op{})} and \cppinline{commutative<T>(Op{})}.
The reason is partial specialisation: "every \cppinline{Rational<I>} is a monoid under \cppinline{+}" is one declaration for a family, and only class and variable templates admit it. A function template cannot be partially specialised, and a constrained overload in its place is found only when it precedes the shape, as Listing~\ref{lst:rule2}'s is, while the library's registrations come after its shapes, in other modules.
So the library is FJlt at its reads and not at its registrations, the adequacy argument covers the listings, not the library, and FJlt's instance resolution is a subset of what the library needs.

\paragraph{The library is part of the toolchain.}
"Standard \Cpp{23}" names a language and a library, and the claim holds for a pair of implementations, not for the standard.
\cppinline{std::bind_front} is standard, and the version in one widely used library does not compile under the compiler this paper uses. The listing that used it now uses a fold instead.
The listings were built with one compiler against two standard libraries, and that is what "compiles as written" means here.
The youngest piece the posture uses is the fold algorithms over ranges, which entered the standard in 2022 and which the library this paper builds with completed in its release 23~\cite{libcxx2026status}.

\paragraph{The compiler has its own budget.}
Constant evaluation is bounded by a step limit the compiler sets, and a program that exhausts it fails to compile.
Rule~3 is what keeps that limit out of the picture: every fold's length is in the program's hands, so the program, not the compiler, decides what is too long, and the limit is a knob to raise rather than a wall to hit.
A fold over a budget has no recursion and meets no depth limit.
A fold over a term is recursion on the term's depth: for a typed term, such as the library's \cppinline{cata} over \cppinline{Compose<F, G>}, it is template instantiation one level per nesting, bounded by \texttt{-ftemplate-depth}; for a term that is a value, evaluated at compile time, it is a recursive \cppinline{constexpr} call per nesting, bounded by \texttt{-fconstexpr-depth}.
Both counters count the depth of a piece of finite data fixed before compilation, which is what Rule~3 makes of a term, and a budget that is a value rather than a type meets no counter at all, so the library's set recursion runs unchanged at runtime.

\paragraph{Undefined behaviour has one binding time.}
Constant evaluation refuses undefined behaviour, so a listing that overflows a signed integer does not compile. At runtime the same program does whatever the hardware does.
This is the only way the two evaluations of Theorem~\ref{thm:simulation} can disagree in \Cpp{} where they cannot in FJlt, and the listings close it by using unsigned carriers, whose arithmetic is total.
A Jlt program on \cppinline{int} is a Jlt program only where its arithmetic cannot overflow, which is a fact about the program that no rule checks.

\section{Related Work}
\label{sec:related}

\paragraph{Type classes.}
Dictionary passing is Wadler and Blott's~\cite{wadler1989adhoc}: a class is a record type, an instance a record, a constraint a parameter, and a constrained call passes the record the compiler resolved.
Table~\ref{tab:dictionary} is that translation with \Cpp{}'s names in the left column, and the row without a counterpart there, structural satisfaction, is the difference Bernardy et al.~\cite{bernardy2010generic} place at the centre of their comparison of concepts and type classes.
Coherence, that a program has one meaning however its constraints are resolved, is where the designs diverge: Racordon et al.~\cite{racordon2025coherence} survey how Haskell, Swift, Rust and Scala keep or trade it, between unique instances and context-dependent resolution.
FJlt takes the strict side by construction, since an instance is a function specialisation and the one-definition rule admits one per head. Theorem~\ref{thm:coherence} is that choice stated as a property of the translation, and the price, that instances for families of types do not fit, is in Section~\ref{sec:limits}.
Rust and Swift also check a generic body against its bounds: a comparison on an unconstrained type parameter is a compile error in both, with the missing bound named in the message~\cite{klabnik2023rust,swift2026generics}.
That is Rule~2 as a compiler check, the half \Cpp{20} dropped, and the posture, together with the checker of Section~\ref{sec:limits}, is what recovering it by hand costs.

\paragraph{Concepts, and the calculus next door.}
The nearest neighbour of Appendix~\ref{app:fjlt} is Siek and Lumsdaine's $F^G$~\cite{siek2005essential,siek2004formalization}: System~F with concepts and models, translated into System~F by dictionary passing, with the translation proved sound in Isabelle.
It was written for the concepts then proposed for \Cpp{0x}~\cite{gregor2006concepts,dosreis2006specifying}, which checked template bodies against their constraints. Those concepts were removed in 2009~\cite{stroustrup2009remove}, and the feature that shipped in \Cpp{20} checks uses and not definitions, which is the gap Rule~2 names.
$F^G$'s models are nominal and can be declared for whole families of types, which is what the library behind this paper's listings needs and FJlt's function-specialisation instances do not provide (Section~\ref{sec:limits}). FJlt is the smaller calculus, and the price of being a subset of a shipped language.
Garcia et al.~\cite{garcia2007extended} compare eight languages' support for generic programming against a fixed design. The rows of their table that \Cpp{} lacked at the time, multi-type concepts and retroactive modelling, are the rows Listing~\ref{lst:monoid} exercises with \cppinline{IsMonoid<T, Op>} and specialisations on types one does not own.

\paragraph{Featherweight calculi.}
Featherweight Java~\cite{igarashi2001featherweight} set the pattern: a core calculus small enough to prove things about, with a syntax that is a subset of the host language's.
Its theorems are proved directly, progress and preservation over its own rules, because type soundness of a language with subtyping has no simpler calculus to inherit from.
Featherweight Go~\cite{griesemer2020featherweight} follows the pattern for structural subtyping and monomorphisation, and \emph{Generic Go to Go}~\cite{ellis2022generic} proves a dictionary-passing translation correct by a bisimulation. That is the genre Section~\ref{sec:guarantees} is in, preservation and simulation of a translation, with soundness, termination and parametricity inherited from the target rather than proved from scratch.

\paragraph{Formal semantics of \Cpp{}.}
CoreC++~\cite{wasserrab2006operational} gives an operational semantics and a machine-checked type safety proof for multiple inheritance; Ramananandro, Dos Reis and Leroy~\cite{ramananandro2011layout,ramananandro2012construction} mechanise object layout, construction and destruction in Coq.
These formalise the part of \Cpp{} that Rule~1 excludes, objects with identity and lifetime, and none covers templates, concepts or constant evaluation, so FJlt is a fragment with its own grammar rather than a subset of a formalised \Cpp{}.

\paragraph{The target.}
Strong normalisation of System~F is Girard's \cite{girard1989proofs}, parametricity Reynolds' \cite{reynolds1983types}, and data types as their own folds B\"ohm and Berarducci's \cite{bohm1985automatic}. The appendix uses the three as black boxes, which is the point of translating into System~F rather than proving about FJlt directly.

\paragraph{What is new here.}
Not the translation nor the calculus-with-concepts, but the claim that the shipped language already contains the fragment, with a calculus whose syntax is that \Cpp{}, listings that run under a stock compiler at both binding times, and an adequacy argument that says where the compiler stops checking and the author starts.

\section{Conclusion}
\label{sec:conclusion}

Three rules on standard \Cpp{23} were stated, and a program that keeps them is, up to the gaps Section~\ref{sec:translation:adequacy} names, a term of a core calculus whose syntax is that \Cpp{}.
The calculus translates into System~F by dictionary passing: concepts to record types, specialisations to records, constraints to parameters, folds to iteration.
The translation preserves types and evaluation and is a function of the program (Theorems~\ref{thm:preservation} to~\ref{thm:coherence}), so a program of the calculus terminates, is parametric and is sound (Corollaries~\ref{cor:termination} to~\ref{cor:soundness}).

What this costs is stated rather than softened.
Two of the three rules are held by the author and not by the compiler, since a template body is checked at instantiation and a loop is not checked for a bound. A tool in the repository narrows the gap (Section~\ref{sec:limits}).
A fold may run out of budget, and when it does the type says so.
Instances for families of types live in tables and are read through functions, so the library behind the listings is Jlt at its reads and not at its registrations.
And "standard \Cpp{23}" names a compiler and a library together (Section~\ref{sec:limits}).

Three things follow as work not done here.
Completing the checker: definition checking proper, over types and arities and the full constraint language, is the distance between the repository's tool (Section~\ref{sec:limits}) and the \Cpp{0x} design, and until it is covered membership in the fragment is a reading the tool narrows, not a verdict it gives.
A mechanisation of the proofs, as Siek and Lumsdaine did for $F^G$ in Isabelle~\cite{siek2004formalization}, so that the theorems hold as stated rather than in sketch.
And algebra, which is where the posture goes next.
The listings here state laws and declare them; over finite ordered carriers equality of functions is decidable and a law can be decided rather than declared, over structures with normal forms the normal form does the deciding, and the same three rules reach that far without change.

Nothing was added to the language, the compiler or the library. What was added is a boundary, inside which a mainstream compiler checks claims of a modest but real kind about programs that then run unchanged, and the posture is available today to anyone with a recent compiler.
