\section{The sugar: closure under the host's constructions}
\label{app:fjlt:closure}
This section names the sugar: each construction of \Cpp{} that a Jlt program writes beyond the kernel's grammar, with its desugaring into the kernel, its condition and no proof; two desugarings, closure conversion and the split of a branch on a constraint, add declarations and so are not local in Felleisen's sense~\cite{felleisen1991expressive}.
The condition is always on how the term is built and never on inspecting it afterwards, so a closure, whose type has no name, can be a term of the calculus.
Tables~\ref{tab:closure} and~\ref{tab:closure:decl} summarise, and the theorems of Appendix~\ref{app:fjlt:theorems} use none of it.
An FJlt program is a Jlt program with the same meaning, provided no law and no \cppinline{static_assert} builds a box (Appendix~\ref{app:fjlt:evaluation}); the converse, for a Jlt program in the grammar, is the adequacy argument of Section~\ref{sec:translation:adequacy}, whose ledger this is.
The listings are FJlt up to this sugar, reading \cppinline{static_assert(e)} as the claim that $e$ evaluates to \cppinline{true}, with two exceptions: Listing~\ref{lst:rule3}'s Collatz chain is finite by fact, not by a condition on $\mathcal{R}$, and Listing~\ref{lst:sites} dereferences an optional in a constant initialiser, admitted under \emph{Sums} below.

\paragraph{Parallelism, and a branch on the binding time.}
\label{app:fjlt:consteval}
\cppinline{std::reduce} may regroup and reorder its operands, so its result is determined only for an operation that \cppinline{IsCommutativeMonoid} certifies, and Rule~1 gives the absence of data races its parallel policies ask.
A parallel \cppinline{concat} is then one more overload, a run-time one, since the policies' overloads are not \cppinline{constexpr}.

\cppinline{if consteval}, and an \cppinline{if} on \cppinline{std::is_constant_evaluated()}, are how a program can observe its binding time, and FJlt need not have them.
\cppinline|if consteval { A } else { B }| desugars to \cppinline{A}, provided \cppinline{B} computes the same value as \cppinline{A} on every input, so that the program cannot observe the difference after all (Table~\ref{tab:closure}).\footnote{The choice of \cppinline{A} is not arbitrary: it is the branch constant evaluation takes, which is FJlt's evaluation, while \cppinline{B} is typically not constant-evaluable, which is why the program branches at all.}
For the parallel \cppinline{concat} the condition is the free monoid's universal property: a fold over a concatenation is the operation applied to the folds of the parts, by associativity, and commutativity lets the parts come in any order.
So the law that licenses the shortcut also proves that the branches agree.
For an arbitrary branch the condition is semantic, and a reader holds it, as for the part of Rule~2 the linter does not reach.

\paragraph{Lambdas.}
A lambda \cppinline{[c...](const τ x...) { return e; }} whose captures are FJlt values taken by copy and whose body is an FJlt term under those captures and parameters is the operation struct with the captures as fields and \cppinline{e} as the body of its call operator.
A generic lambda written with a template head and a \cppinline{requires} clause is the operation with a generic call operator.
The reason is the standard's own definition of the closure type: a class with the copied captures as members and a \cppinline{const} call operator, which is the function object production of Figure~\ref{fig:fjlt-syntax} to the letter.
Capture by reference is excluded by Rule~1 before this lemma is reached.
A capturing closure type is copy constructible and neither default constructible nor assignable, so it is not \cppinline{std::semiregular} and Rule~1 does not admit it as a value; it is admitted as sugar, judged through its image, which is semiregular when its captures are.
That is the general rule for sugar: the rules are asked of the kernel term.
A closure type has no name, so a lambda is never a carrier and never the head of an instance, and nothing in the statement asks to look inside it once built.

\paragraph{\texttt{if constexpr} on a value.}
A body \cppinline{if constexpr (p) return A; else return B;} with \cppinline{p} a closed \cppinline{bool} term, a law or a trait read, and \cppinline{A}, \cppinline{B} FJlt terms of one type under the same context, is the term \cppinline{p ? A : B}.
The condition is stronger than \Cpp{} asks, since \Cpp{} does not instantiate the discarded branch and FJlt types both, and the compiler decides it: the rewritten body compiles or it does not.
Constant evaluation of the two spellings agrees because both evaluate \cppinline{p} first and then one branch.
Whether the two branches share a type is decided per site by the rewrite, and a site whose branches differ in type, \cppinline{lattice_term}'s \cppinline{Meet<RA, RB>} against \cppinline{Meet<RB, RA>}, is not this row but a branch on types in a value's clothing, and waits with the next.

\paragraph{\texttt{if constexpr} on a constraint.}
A body \cppinline{if constexpr (C<T>) return A; else return B;} in a generic function with head $\overline{Q}$, where \cppinline{A} is an FJlt term under $\overline{Q}, C\texttt{<T>}$ and \cppinline{B} one under $\overline{Q}, \texttt{!}C\texttt{<T>}$, is the pair of generic functions with those two heads.
The pair plays the role of a two-clause instance chain of Morris and Jones~\cite{morris2010instance}, an explicit alternation decided by one constraint, though here resolution by specificity (Appendix~\ref{app:fjlt:typing}) rather than clause order picks its branch: at a concrete type the compiler decides $C\texttt{<T>}$, and at a type variable the call resolves only where the enclosing context decides it.
A call it cannot decide is the next row's.
When the test is \cppinline{std::same_as<T, X>} at a concrete \cppinline{X} and \cppinline{T} is the whole head, the first function is an explicit specialisation at \cppinline{X}.
A test of a \cppinline{requires} expression written in the body is not a declared constraint under Rule~2, and the tool's \texttt{inline-requires} check holds the module at zero.

\paragraph{A call its clause does not decide.}
A generic function whose body calls a chain at its own type variable, without a clause that entails the chain's constraint or its negation, varies with the type through a constraint it did not declare.
\Cpp{} accepts it and resolves the call at each instantiation; the kernel refuses it, by GHC's rule.
Its desugaring is constraint inference: the call's resolution becomes a parameter of the enclosing function, which each caller supplies after resolving it at a concrete type, where resolution is a function, so the kernel term agrees with what \Cpp{} instantiates.
The price is in the free theorem, which now ranges over that parameter.
Written by hand, the same thing is to decide the constraint in the clause, by requiring it or by splitting on it.

\paragraph{Sums.}
The kernel has the case form (Table~\ref{tab:conventions}), so given FJlt terms \cppinline{f} and \cppinline{g} on the two summands their copairing is an FJlt term, \texttt{case(}$s$\texttt{, }$f$\texttt{, }$g$\texttt{)}.
\cppinline{has_value} and \cppinline{value_or} on an optional are that case on $1 + T$, and \cppinline{std::visit(O{}, v)} is the case whose branches are one generic call operator entailed at each summand.
\cppinline{*} on an optional is partial, undefined on the empty one, and is admitted under a \cppinline{has_value} guard, which desugars to the case form, as the head of a range is admitted only when its length is positive, or in a constant initialiser, where constant evaluation refuses the empty case and the compiler holds the guard, as for Listing~\ref{lst:sites}'s \cppinline{*automaton(sites)}.
\cppinline{std::get} on a variant is partial too and is not admitted: a variant is read by the case form.

\paragraph{Variable and class templates.}
A variable template \cppinline{v<T...> = e} is the nullary function template \cppinline{v<T...>() { return e; }}, and a class template with a static constant member is the same, since constant evaluation of the three agrees.
A partial specialisation over a family, every \cppinline{Rational<I>} under \cppinline{+}, is an instance with a context, in the grammar.
Nothing is missing for one family; a primary that answers \cppinline{false} beside families that answer \cppinline{true} is two generic functions whose heads both match, which resolution by specificity orders.
The host's lookup wall (Section~\ref{sec:limits}) makes the FJlt spelling unwritable in the library's module layout; the library's spelling is FJlt by this statement.

\paragraph{Member functions.}
A \cppinline{const} member function \cppinline{τ m(τ x...) const { return e; }} of an operation is the generic function \cppinline{m(O self, τ x...)} whose body reads the fields of \cppinline{self} where the member read \cppinline{this}.
A static member function is a generic function.
A struct with fields and no call operator is a product, nested pairs.
Rule~1 supplies the \cppinline{const}, and the body is FJlt by hypothesis, so nothing is missing.

\paragraph{Abbreviations.}
An alias template is substitution.
\cppinline{std::tuple} of FJlt types is nested pairs.
\cppinline{std::array<T, n>} is a product of $n$ copies and also a member of $\mathcal{R}$, with length $n$, a head and a tail, so a fold over it is already in the grammar.

\paragraph{Overloading.}
Overloads of one name at distinct concrete carriers are explicit specialisations of one trait.
Constrained overloads are generic functions, and where their heads both match, resolution by specificity orders them, as for Listing~\ref{lst:laws}'s overloads of \cppinline{fold} and \cppinline{concat}.

\paragraph{Inheritance.}
Jlt has no subtyping: the grammar has no base clause and no derived-to-base conversion, a class with a base that holds state or a virtual function is outside the posture, and the tool's \texttt{inheritance} check holds the module at zero.
What the library writes with a base clause is a registration, \cppinline{struct is_involutive<X> : std::true_type}, every base an empty class: the family row spelled by inheritance, read as the fact it states.

\paragraph{What the table says.}
The table is complete by measurement, not by argument, at the resolution of a syntax node's kind: the repository's tool lists every kind the \texttt{category} module and the listings write, leaving out the compiler's implicit wrappers, and each is the kernel's or a row of the table.
A kind does not tell every use apart: a binary operator is arithmetic or an assignment, and the assignments are the row of local state, which Rule~1's footnote admits and which reading, not counting, finds.
With the table closed, the second direction of Section~\ref{sec:translation:adequacy} reads: a Jlt program built from the grammar by these constructions under their conditions is an FJlt program.
